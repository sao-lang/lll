# 设计稳定性门禁（G5 · 契约锁）

> 目的：防止"设计方案改动 → 已实现功能被迫重构"的危险。
> 机制：把已实现模块（R1/R2）的公共契约固化为带哈希的锁文件，任何漂移立即失败。
> 实现：`tests/tools/contract_lock.py` + `tests/tools/contract_lock.json`（基线）。
> 注：本文 §1/§2 出现的 `scratchpad:`、`tests/m1/`、`R1~R11` 等旧值均为**被禁止契约的示例**，非现行用法；G5 扫描器不会对本文做锚点校验。

---

## 1. 为什么需要这道门禁

本次（2026-11-17）设计一致性审查发现 12 处缺陷，共同模式是：
**设计文档被改写或代码被重构后，两边不再一致，但没有任何机制拦截**——
- 代码字段 `scratchpad` 改成了 `scratch`，文档还写旧名；
- 文档承诺 `Hook.matcher` 过滤，代码根本没实现；
- 验证矩阵指向早已删除的 `tests/m1/`。

这类漂移一旦进入后续开发，就会导致"照文档写的代码跑不起来"或"改设计就要重构已实现功能"。G5 就是把"已实现的东西"锁住，改动必须显式评审。

## 2. 锁什么

### 2.1 代码契约（AST 自动提取，65 项符号）

对 `src/runtime/` + `src/hooks/` 的每个公共类，锁定三样：
- **fields**：dataclass / 类的公开字段
- **methods**：公开方法名
- **enum_values**：枚举值（如 `EffectKind` 的 6 个值、`DecisionAction` 的 8 个值）

任何增删改都会改变基线哈希 → 门禁失败。

**边界速查（哪些改动触发、哪些不触发）**——提取器 `extract_contract()` 只处理 `ast.ClassDef` 且 `not node.name.startswith("_")`：

| 改动 | 是否触发 G5 |
|---|---|
| 新增非下划线公共类 | ✅ 触发（"新增公共契约"） |
| 增删改公共类字段 / 方法名 / 枚举值 | ✅ 触发（破坏性，需评审） |
| 新增下划线开头的私有类 / 私有方法 / 私有函数 | ❌ 不触发 |
| 修改方法体（签名不变） | ❌ 不触发 |
| 修改模块级类型别名（如 `DispatchFn`） | ❌ 不触发 |
| 补注释 / 补类型注解 | ❌ 不触发 |

**含义**：可在私有命名空间内自由重构（如新增 `_Verdict` 视图、`_coerce_*` 归一化函数、私有枚举），无需改基线；一旦要把 helper 提升为公共 API 或改动公共类结构，才走 §4 评审。这条边界是编码规则 9 的判定依据。

### 2.2 设计文档契约锚点

| 文档 | 必须出现 | 禁止出现 |
|------|---------|---------|
| R1 模块文档 | `scratch:` / `tests/r1/` / `EffectKind` / `WAIT_HUMAN` | `scratchpad:` / `tests/m1/` / `make demo-m1` |
| R2 模块文档 | `HookMode` / `DecisionAction` / `OBSERVE` / `ABORT` / `tests/r2/` | `tests/m2/` / `tests/m3/` / `matcher: Matcher` |
| AGENT-总设计 | `10 内置架构` / `R1~R13` / `scratch` | `11 内置架构` / `R1~R11` / `scratchpad:` |

防止有人把设计文档改回旧值，造成"文档与已实现代码不符"。

## 3. 怎么用

```bash
# CI / 提交前：检查（只读，不改文件）
.venv/Scripts/python.exe tests/tools/contract_lock.py check

# 评审通过后：更新基线（会改 contract_lock.json）
.venv/Scripts/python.exe tests/tools/contract_lock.py update

# 已接入统一门禁：
.venv/Scripts/python.exe tests/tools/gate_check.py --module r1   # 含 G5
.venv/Scripts/python.exe tests/tools/gate_check.py --module r2   # 含 G5
```

## 4. 变更流程（强制）

```
想改 R1/R2 的公共 API 或设计文档契约
   ↓
① 判断是否兼容扩展（只加字段/方法，不改不删）
   ├─ 兼容 → 确认测试通过 → contract_lock.py update → commit 标注 [CONTRACT] 变更点
   └─ 破坏性（改字段/删方法/改枚举）→ 必须走架构评审
         ↓
      ② 评审记录写进 commit message（BREAKING），说明为何值得让已实现功能返工
      ③ update 基线 → 全量门禁重跑 → 合入
```

**禁止**：直接 `update` 绕过评审来让门禁变绿。门禁日志会显示每处精确 diff，reviewer 可核对是否合规。

## 5. 门禁失败时怎么读

```
[G5] FAIL ...
  - runtime.types.PortError.fields: ['code','message','retryable'] → ['code','message']
```
含义：`PortError` 的 `retryable` 字段被删。若非本意 → 恢复代码；若确为设计变更 → 走评审。

```
  - R1 文档 出现已废弃契约 'scratchpad:'
```
含义：文档回退到旧字段名。应改回 `scratch`，否则后来人按文档写会 AttributeError。

## 6. 新模块纳入锁定的时机

R3~R12 实现后，把其包名加进 `contract_lock.py` 的 `LOCKED_PACKAGES`，运行 `update` 生成新基线，并在 `DOC_ANCHORS` 补该模块的契约锚点。**未实现的模块不锁定**（ design 可自由迭代）。

## 0. 先回答"protocols.py 为什么每个 Port 都是 `...`"（用户同批提问）

**两层原因，必须分开看：**

**第一层（合理）：这是 Protocol 的语法要求，不是偷懒。**
`src/hooks/protocols.py:12-13` 文件头明写：「每个 Protocol 方法签名即契约（参数 + 返回值全部标注）；
方法体统一 `...` 占位，具体实现由注入的适配器提供」。R2 文档 §1（第 10-11 行）规定 R2 **"做"定义全部对外协议契约，"不做"具体能力实现（R3~R9）**。
`typing.Protocol` 的方法体本来就该是 `...`——它是接口，类里写实现反而错了。
`PORT_PROTOCOLS` 表（第 234-239 行）用于装配期 `isinstance` 履约校验。所以 13 个 Port 全省略是**设计如此外观**。

**第二层（真问题）：框架里一个真实 Port 实现都没有。**
Bash 实测 `grep -rE 'class .*\((LLMPort|ToolPort|...)\)' src/` → **零命中**。
R13 文档 §3 规定可插拔四要素缺一即"假可插拔"：①协议 ②默认 ③入口 ④校验。
现状是 ①有（protocols.py）④有（PORT_PROTOCOLS + Registry）③有（register/replace），
**②默认实现普遍缺失**。各模块文档其实写了"默认应该是什么"——

| Port | 文档规定的默认 | 出处 |
|---|---|---|
| LLMPort | OpenAI-compat | R4 §6（第 93 行） |
| ToolPort | ToolRegistry | R5 §6（第 104 行） |
| SkillPort | 文件技能 | R5 §6（第 106 行） |
| MemoryPort | 内存/向量 | R7 §6（第 88 行） |
| SandboxPort | 进程隔离 | R9 §6（第 75 行） |
| AuditPort | 本地日志 | R9 §6（第 77 行） |
| EvalPort | 本地回归/LLM-judge | R10 §6（第 90 行） |

但这些默认全部"设计中有、代码里无"（对应模块 R5~R10 都是待实现）。
所以准确说法：**`protocols.py` 全省略是对的；错的是它承诺的 13 个默认实现，一个都没落地。**

## 3. 结论

**是的，设计文档大量不完整，但性质要分清：**

- **骨架层（模块划分、总流程、Hook/Decision、门禁规则）**：完整，可直接指导实现——R1~R4 就是照它做出来的。
- **接口层（协议签名、DTO）**：大体完整，但有少量漂移（R4 route 返回类型、总设计架构数量）。
- **实现细节层（算法、参数默认值、状态机、错误语义、跨模块编排）**：大量缺失，尤其 R5~R13 与 R4 流式——照文档写代码会卡住，必须自己补设计。
- **默认实现层**：13 个 Port 的默认实现全部只有名字没有代码（对应模块待实现）。

**给排期的建议**：R6 最接近"可直接写码"（参数表较全、个别"—"待定）；R8/R13/R11 最需先补设计；任何模块动手前应先做一次"设计深度体检"——本报告的方法可复用（读头部状态 → 查 src 包 → 读 §4 签名 → 找状态机/参数表）。

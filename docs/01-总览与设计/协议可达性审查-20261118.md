# R1~R4 协议可达性审查（2026-11-18）

> **审查维度**（区别于之前的"有没有实现"）：**协议承诺的能力，实现者拿到的输入够不够真正做到？**
> 起因：`SemanticCache` 协议名承诺语义匹配，但 `get(key: str)` 只收到不可逆哈希——语义缓存拿不到原文，
> 能力不可达。本报告用同一维度把 R1~R4 全部 Protocol 过一遍。
> 结论依据：协议签名（src/**/*.py）+ 调用点 + DTO 真实字段。只审查不改代码。

## 2. 🔴 不可达：SemanticCache（已确认，待修）

**证据链**：
- `cache.py:22` `get(self, key: str, *, version: str)` —— 只收哈希串
- `gateway.py:82` `key = build_cache_key(request, ...).value`
- `types.py:65-84` `cache_key_string()` = sha256(messages+model+params+version) → **不可逆**
- 语义缓存需要 query 原文算相似度，但拿到的是 32 位哈希 → **无法兑现"语义"承诺**

**根因**：key 计算归属错了——放在网关侧，缓存实现永远只见到哈希。
**修法**：协议改接 `LLMRequest`（缓存实现自己决定 key 策略），ExactCache 内部仍算哈希（行为不变）。

## 3. ⚠️ 有缺口：逐个分析

### 3.1 Hook 的 8 action 承诺 vs 内核只消费 4 种
- `DecisionAction` 定义了 8 种（CONTINUE/REWRITE/DENY/ASK/RETRY/DEGRADE/FALLBACK/ABORT）
- `types.py:51` 代码注释自承："当前 R1 内核真正消费的是 continue/deny/abort/fallback；
  rewrite/ask/retry/degrade 属 R3/R4/R9 未实现模块的动作，载体已定义"
- **可达性**：协议承诺 8 种控制力，已实现内核只兑现 4 种。其余 4 种要等对应模块——
  这是"跨模块依赖"而非局部缺陷，但文档措辞（8 action 全生效）曾造成误解（旧审查已修）。
- 判定：**⚠️ 分阶段可达，非 bug**

### 3.2 ToolPort.call 的 ToolCall 无 danger/source
- `ToolCall` 只有 call_id/name/args（`dto.py`），danger/source 在 `ToolSpec`（注册表里）
- R9 设计"danger 路由"要求高危工具走沙盒+审批——但执行 Port 的 `call(call, ctx)` 拿不到 danger
- 可行路径：ToolPort 实现内部查 registry 补 danger（能做到，但要实现者知道额外查表）
- 判定：**⚠️ 可达但绕弯**；建议 ToolResult.meta 或 call 签名带上 danger

### 3.3 SandboxPort.run(fn: Callable, ...) —— 进程隔离不可达
- 签名 `run(self, fn: Callable[..., DynamicValue], args, ctx)`（`protocols.py:175`）
- **进程隔离沙盒**要能把 fn 序列化传到子进程/容器；普通 Python Callable 不可跨进程（闭包/lambda/绑定方法都不行）
- 当前只能做"同进程隔离"（线程/超时），真沙盒需改成接收代码字符串或可序列化 spec
- 判定：**⚠️ 承诺"沙盒"但签名只够"同进程执行"**——R9 实现时会撞上

### 3.4 AuditPort.record(event: dict) —— 防篡改缺字段
- 协议 `record(event: dict[str, DynamicValue], ctx: PortCtx)`（`protocols.py:187`）
- R9 DTO 设计里 AuditEvent 有 prev_hash/hash（哈希链），但协议的 event 是裸 dict，
  实现者要自己约定哈希链字段 → 不同实现互不相通
- 判定：**⚠️ 可达但契约不统一**；建议协议直接收 `AuditEvent` 具名类型

### 3.5 EvalPort.score(case_id: str, ...) —— 评测器拿不到 case
- 协议只给 case_id（字符串 id），`output: DynamicValue`
- 评测打分需要 expected/expected_trajectory/should_refuse（R10 EvalCase 字段）——实现者得自己再查库
- 判定：**⚠️ 可达但多此一举**；建议 score(case: EvalCase, ...)

### 3.6 TelemetryPort 的归因维度藏在 meta
- `span(name, ctx)`/`metric(name, value, tags)`：PortCtx 显式字段是 session_id/run_id/trace_span/budget_left/meta
- 成本归因要的 agent_id/user_id 在 `ctx.meta` 里，靠 `coerce_port_ctx()` 具名边界读（`_ctxview.py`）
- 能读到（规则 6 边界已建），但不是协议显式字段——实现者不看 _ctxview 就会漏归因
- 判定：**⚠️ 可达但靠约定**

### 3.7 HumanPort.ask 的 resume 点未显式
- `ask(question, options, ctx) -> str`：只返回答案字符串
- 挂起→审批→resume 的"续跑点"靠 A5 CancellationToken / checkpoint 承载（R1 设计有）
- 协议签名没表达"这次 ask 对应哪个挂起点"——多轮并发审批时可能串线
- 判定：**⚠️ 可达但需调用方自律**

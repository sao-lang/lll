# 增强器封装指南（去角色化重写：领域策略 + 可靠性执行器）

> **历史说明**：本指南原名讲 **AOP 五角色增强器**（`Prelude`/`Warden`/`Envelope`/`Refiner`/`Salvage` + `aop.Role` 枚举 + `AOPContainer.register(Role.X, e)`）。用户审计确认 CompositeCall 只是 AOPContainer 改名，已要求五角色语义（名字 + 相似逻辑）从代码与文档彻底删除。本文按 2026-11-22 去角色化迁移卡重写为**领域策略 API**；"增强器/角色"仅在此历史说明中出现，不代表当前架构。
> 现行做法：把横切可靠性能力写成**有自身领域方法的策略实例**，用 `ResilienceCapability` 具名构造注入，由 `ReliabilityExecutor` 显式编排（前置放行 → 预算内中心调用 → 熔断记数 → 失败降级选级 + 重路由）。
> "插件"一词在本项目专指 **Lifecycle 通知订阅者**（只做事、不拦截），另见[《插件封装指南》](./插件封装指南.md)。依赖方向恒为 策略/插件 → 装配层 → 内核，内核零依赖扩展组件。

---

## 一、先说结论：横切"怎么执行"的三条路

```
① 横切"怎么执行"（how）—— 领域策略（R3 执行器）/ call 装饰器 ← 本指南
     R3 领域策略（src/harness/resilience/）：9 个策略各暴露自身领域方法
     KillSwitch.is_tripped / Watchdog.detect / Idempotency.check_and_mark
     RateLimit.acquire→RatePermit / Bulkhead.run_in_slot
     CircuitBreaker.permit+observe_outcome / RetryPolicy.run_with_retries
     Timeout.run_with_deadline / Degradation.select
     由 ReliabilityExecutor 显式编排，无角色协议、无 Role 枚举、无槽位列表

② 横切"发生了什么"（when）—— Lifecycle 插件（compose.notify）
     只读通知、不拦截、不改写，异常就地隔离 → 见《插件封装指南》

③ 新流程 / 新能力
     新执行流程 → Program（yield Effect）
     新外部能力 → Port（实现 Protocol + registry.register）
```

**策略能碰到的内层**：

- `Invocation`（`compose.context` 的统一上下文）：`effect`（当前 `Invoke`）+ `ctx`（RuntimeCtx）+ `session` + `meta`（故障经 `FaultRecord(reason, failed_target)` 具名记录直传，非裸键容器）。请求期输入经领域方法参数直传，装配期配置走构造参数注入。
- `next` / `core`：`run_in_slot(inv, next)` / `run_with_retries(inv, next)` / `run_with_deadline(inv, next)` 收到的下一跳回调；最内层 `core` 是中心 Port 调用（如 `ModelGateway.as_call`）。由 `ReliabilityExecutor` 包裹并调用。
- 跨调用状态由**策略实例自身**持有：熔断三态机、降级 ladder+available+按会话目标状态直接放在实例上（注册一次、长期存活，天然跨调用）；装配期配置由构造参数注入。无独立 Policy 层。

**策略不能碰的**：`State` 是 frozen（要改走 R7 的投影点或 A 类 `map_effect` 改写 Effect payload，**不写回** `State.messages`）；策略**不声明**调用语义或优先级——顺序由 `ReliabilityExecutor` 显式编排固定；`Notice`（Lifecycle 只读载荷）不是策略上下文，别把通知当拦截通道用。

## 二、9 领域策略（方法名即领域行为，不共享统一协议）

| 领域策略 | 执行器调用的领域方法 | 直觉 | 典型用途 |
|---------|---------------------|------|---------|
| `KillSwitch` | `is_tripped(session_id) -> bool` | 紧急开关 | 置位即终止拒绝（人工一键停服） |
| `Watchdog` | `detect(inv) -> bool` | 循环探测 | 重复 / A-B 交替命中即终止拒绝 |
| `Idempotency` | `check_and_mark(key) -> bool` | 去重认领 | 窗口内重复副作用即终止拒绝 |
| `RateLimit` | `acquire() -> RatePermit` | 令牌桶 | ADMIT 放行 / REJECT 终止 / DEGRADE 写 fault |
| `Bulkhead` | `run_in_slot(inv, next) -> Result` | 舱位隔离 | 占槽 → 下一跳 → `finally` 释放 |
| `CircuitBreaker` | `permit(inv) -> str\|None` + `observe_outcome(inv, result)` | 熔断三态 | OPEN 写 fault 交降级；调用后记数 |
| `RetryPolicy` | `run_with_retries(inv, next) -> Result` | 退避重放 | 耗尽写 fault（R3-7） |
| `Timeout` | `run_with_deadline(inv, next) -> Result` | 调用级超时 | 超时写 fault（R3-7） |
| `Degradation` | `select(fault, session_id) -> str` | 唯一降级裁决者 | 保 B1/B2/R3-6/R3-7 四坑 |

> 每个策略**只暴露自身的领域方法**，不实现任何 `guard()`/`wrap()`/`recover()`/`observe()` 统一协议；没有 Role 枚举或角色槽位列表。故障信号统一走 `FaultRecord(reason, failed_target)`，不再是通用 `Verdict(allowed)`。

## 三、三种典型领域策略

### 方式 1：包裹下一跳的策略 —— 重试（最常用）

```python
from harness.resilience import RetryPolicy
from runtime import Result

class MyRetryPolicy(RetryPolicy):
    """重试策略：按退避预算重放下一跳，耗尽写具名故障记录。"""
    name = "my-retry"

    # run_with_retries(inv, next) 由 ReliabilityExecutor._budgeted_call 调用；
    # 耗尽时写 FaultRecord(reason="retry_exhausted", failed_target=target_of(inv))（R3-7）
```

**能做什么**：在 `next(inv)` 前后算耗时、包装 Result、失败退避重放；**不调 `next` 可直接短路**；失败写 `FaultRecord` 交 `Degradation.select` 裁决。
**要改请求内容**（预算/软限）：用 A 类 `map_effect` 算子改写 `Invoke.payload`，不要在策略里塞参数。

### 方式 2：前置放行类策略 —— 紧急开关

```python
from harness.resilience import KillSwitch

class MyKillSwitch(KillSwitch):
    """紧急开关：标志置位时拒绝调用。"""
    name = "my-killswitch"
    # is_tripped(session_id) -> bool：执行器 _preflight 首判，
    # True → _reject("killswitch")，发 invoke_rejected，不调 core
```

### 方式 3：降级裁决策略 —— 跨调用状态由实例自身持有

```python
from harness.resilience import Degradation
from compose.context import FaultRecord

class MyDegradation(Degradation):
    """降级裁决者：状态直接在本实例上（P9 四坑）。"""
    name = "my-degrade"
    # 构造传 ladder + available + 可选 session_state
    # select(fault: FaultRecord, session_id) -> str：
    #   B1  按 session_id 取独立状态切片（禁容器级单值）
    #   R3-6 把 fault.failed_target 永久从本会话 available 剔除并写回
    #   沿 ladder 由高 quality 选可用 target；空集 → "refuse"（禁止编造）
```

### 装配示例（领域策略的唯一拼接方式）

```python
from harness.resilience import (
    DegradeLadder, DegradeStep, DegradeMode, Degradation,
    KillSwitch, ResilienceCapability, RetryPolicy,
)
from harness.model import ModelCapability
from runtime import Runner

cap = ModelCapability(llm=my_llm_port)
ladder = DegradeLadder(steps=(
    DegradeStep(target="primary", mode=DegradeMode.REROUTE, quality=1.0),
    DegradeStep(target="backup",  mode=DegradeMode.REROUTE, quality=0.6),
    DegradeStep(target="",        mode=DegradeMode.REFUSE,   quality=0.0),
))
reliability = ResilienceCapability(
    killswitch=MyKillSwitch(),
    retry=MyRetryPolicy(),
    degradation=Degradation(ladder, available={"primary", "backup"}),
).install(core=cap.gateway().as_call())     # → ReliabilityExecutor

# R1 注入点：call 槽吃下执行器产出的 CallFn，Runner 不感知可靠性细节
runner = Runner(call=reliability.as_call())
```

- 策略 **opt-in**：不传即缺席，执行器跳过该领域步骤，无占位实现。
- `extra_plugins` 只接受**函数式 `(CallFn) -> CallFn` 变换器**（非 callable 装配期 `ValueError`），不是角色插件：

```python
def trace_transform(nxt):
    async def wrapped(inv):
        ...                      # 前置观察
        result = await nxt(inv)
        ...                      # 后置观察
        return result
    return wrapped

reliability = ResilienceCapability(extra_plugins=(trace_transform,)).install(core)
```

要同时接 Lifecycle 通知（审计/观测），用 `runner_notifier(bus)` 桥接 `Runner(notify=...)`，玩法见[《插件封装指南》](./插件封装指南.md)。**领域策略与 Lifecycle 插件是两套体系，各自独立装配，只在装配层汇合。**

## 四、如果功能复杂到策略装不下怎么办

领域策略适合**横切可靠性行为**（放行 / 包裹 / 记账 / 兜底）。如果你要的是**全新的执行流程**（比如一个新的多 Agent 架构、自定义规划器），正路是写 **Program**——框架铁律是"架构即 Program"：

```python
def my_custom_flow(state: AgentState):
    """自定义流程就是一个 generator，yield Effect 声明要做什么。"""
    plan = yield Invoke(port="llm", payload={"messages": [...]})        # 声明，不执行
    results = yield [Invoke(port="tool", payload={"call": s}) for s in plan["steps"]]
    yield Terminate(output=summarize(results), reason="done")
```

Program 里只能 yield 四种 Effect：`Invoke` / `Spawn` / `Suspend` / `Terminate`。如果确实需要**新的外部能力**（比如向量库、浏览器），走 **Port 替换**——实现对应 Protocol，注册进 Registry（Port 注册名必须 ∈ `PORT_PROTOCOLS`，不可新增种类）：

```python
class MyVectorStore:
    name = "my-vector-store"
    async def upsert(self, chunks): ...
    async def search(self, vec, top_k, filters): ...
registry.register("rag", MyVectorStore())   # 协议替换，上层零改动
```

三条路的选择：

- **横切"怎么执行"** → 领域策略 + `ResilienceCapability` 具名注入 ← 本指南
- **横切"发生了什么"** → Lifecycle 插件（`name` + `register(bus)`，`bus.on` 订阅）→ 《插件封装指南》
- **新执行流程** → Program（yield Effect）
- **新外部能力** → Port（实现 Protocol + `registry.register`；Port 种类不新增，`x-*` payload 扩展键保留）

## 五、怎么写一个好的领域策略（领域指导）

1. **职责单一**：一个策略只做一类领域行为（放行判定 / 包裹执行 / 记账 / 选级），别把多类混在一个类里——要覆盖多个领域就注入多个策略。
2. **留名**：`name` 必填且稳定，trace 与诊断全靠它。
3. **显式声明依赖**：要用哪个 Port / 时钟 / 存储就从实例构造参数显式注入；跨调用状态由实例自身持有、随装配长期存活。
4. **别吞主流程异常**：包裹类策略该抛出就抛出；降级意图写 `inv.write_fault(FaultRecord(reason, failed_target))`，由 `Degradation.select` 统一裁决；不要直接改别人的状态或搞容器级单值。
5. **用具名记录而非隐式耦合**：故障经 `FaultRecord(reason, failed_target)` 传，目标经 `RoutingTarget` 传，别塞裸键。
6. **单一上下文**：用 `Invocation`（effect/ctx/session/meta），不另建一套状态；`Notice` 是 Lifecycle 的只读投影，不属于领域策略。
7. **不声明调用语义/优先级**：顺序由 `ReliabilityExecutor` 显式编排固定，策略只实现自己的领域方法。
8. **不改运行时内核**：Effect / State / Result 是框架的确定性契约，策略只经 `compose.context` DTO 交互。
9. **压缩/记忆不进内核**：上下文压缩走 R7 显式编排 + 投影点（A 类 `map_effect` / `ctx_factory`），不写回 `State.messages`。

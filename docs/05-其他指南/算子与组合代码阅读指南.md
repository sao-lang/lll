## 0. 一句话心智模型

**R1 是唯一执行循环，只认三样东西：Program、call、notify。combine 层（src/compose）是整个框架的装配中枢——它把工具层装配成 Program、把能力装成 call，然后注入 R1。AOP/LifecycleBus 已取消，其能力全部归位到 compose。**

```
工具层(R3-R7+用户) → 组合层(compose 算子+call) → 核心层(R1)
依赖只向下；R1 零依赖扩展组件；compose 是唯一知道"有哪些工具层"的地方
```

## 第 1 站 · R1 边界：先搞清内核认什么、不认什么

**读什么**
- `src/runtime/types.py:560-561`（Effect 四类联合 `Invoke|Spawn|Suspend|Terminate`）、`:724-725`（`CallFn` 签名）、`:337+`（AgentState）
- `src/runtime/runner.py:190-212`（构造注入点 `call`/`notify`）、`:300-322`（分派 + 唯一 call 调用点）、`:511-530`（并行 gather + 按序回注）
- `src/runtime/interpreter.py:153-162`（认非空 `list[Effect]` 为并行批）

**抓什么**
- R1 只做机制：Effect 分派、预算预检/扣减、fold 折叠、事件/快照、取消。
- **call 只覆盖 Invoke**：`Spawn` 在 `_execute` 入口被截走（`runner.py:312-313`），`Suspend`/`Terminate` 在批次层走快路径（`runner.py:491-509`）。唯一的 call 调用点是 `runner.py:322`。
- 并行真相：R1 里**没有 `EffectBatch` 公开类型**（它是 interpreter 内部类，`interpreter.py:30/150/162`）。并行靠 generator 一次 `yield [e1, e2]`，runner `asyncio.gather` 后按序回注 list。

## 第 2 站 · A 类算子：Program 怎么被装配

**读什么**
- `src/compose/__init__.py:1-100`（公共 API 全景：①A 类 10 算子 + `call.py` 函数式装饰器/`build_call` + DTO + hooks 归位资产；**无 `AOPContainer`/`CompositeCall` 别名**，五角色符号已物理删除）
- `src/compose/program.py` 全文，重点：
  - `:1-14` 文件头约束（纯变换、状态进 x-*、gate 唯一可挂起）
  - `:48` `ProgramFn = Callable[[], Program]`（工厂层变换，resume 靠重建）
  - `:51-58` `_Keys`（x-compose.* 私有 scratch 键）
  - `:68-142` 三机制：`_as_state`（回注归一）、`_run_child`（驱动子 Program + 拦截 Terminate）、`_as_program`
  - `:145-485` 10 算子：`seq/par/branch/race/loop/map_state/map_effect/fallback/gate/retry`
- `src/compose/tool_layer.py:20-48`（`layer_program`：工具层的 build() 外壳）
- `src/archs/base.py:17-65`（Arch/JoinStrategy 协议）+ `src/archs/recipes.py:28-54,80-97,168-186,229-263`（ReAct/Supervisor/Graph 配方）

**抓什么**
- **三个协作机制**：
  - `_as_state`（`:68-86`）：把回注值归一为可读 State（本身是 State 原样、dict 造 scratch、其它空 State）。
  - `_run_child`（`:106-133`）：驱动子 Program，拦截其 `Terminate` 取 output（不转发 R1，避免提前结束整个 run），从 effect.payload 抽 `x-` 键合并进局部 state。
  - x-* carry：算子间数据传递全靠 scratch 的 `x-compose.*` 键，组合层自持，R1 fold 不感知。
- **par/race 真并行**（刚修复）：`par:201-253` 用 lockstep 调度——每子一个 generator，每轮把各子当前 Effect 汇成一个列表**一次 yield**（走 R1 并行），回注 list 按槽位 send 回各子；子 Terminate 拦截 output，全完成按 `_join_outputs`（`:175-198`，any/majority/all）聚合。**race** `:285-334` 同构，首胜即停（取消交 R1）。
- 架构 = 算子的预设配方（2026-11-23 全部 10/10 真实复用）：ToolUse=`par`/`reduce(seq)`、ReAct/PlanExecute/Reflection/Handoff/Graph=`loop_until`（回注值驱动）、Router/RouterSkill=`branch_value`（值驱动分支）、Supervisor/Blackboard=`par`。`loop_until`/`branch_value` 不读 `port="state"`（真实 Runner 无此 port）。

## 第 3 站 · call 链：能力怎么被装进 call

**读什么**
- `src/compose/call.py`：`retry_call`/`timeout`/`danger_route`/`injection_guard`（③函数式装饰器）、`build_call(base, *, decorators=())` —— 函数式 call 装配入口（原 `Guard`/`with_guard`/`Verdict` 拦截协议已删除）
- `src/compose/dispatch.py`：`dispatch`/`make_dispatch` 按 port 分派、异常折叠 Result
- `src/compose/guards.py`：`FaultRecord`/`RoutingTarget`/`CallState` 具名协作 DTO，无拦截逻辑（原 `DegradationGuard`/`degrade_retry` 已删除）
- `src/harness/resilience/executor.py`：`ReliabilityExecutor` 显式编排（前置放行 → 预算执行 → 熔断记数 → 降级选级 + 重路由）
- `src/harness/resilience/capability.py`：`ResilienceCapability` 具名构造注入 9 领域策略，`install()` 产出执行器
- `src/harness/resilience/defenses.py` / `breaker.py` / `retry.py` / `timeout.py` / `types.py`：9 领域策略领域方法与共享类型

**抓什么**
- **函数式装饰器装配（compose/call.py）**：`build_call(base, *, decorators=())` 把 ③ 装饰器按内层先注册顺序组合（base → decorators[0] → …）；原 `with_guard`/`guard.check`/`guard.observe` 拦截协议已删除，不再有 guards 最外层包裹。**R3 可靠性链不走这里**，由 `ReliabilityExecutor.as_call()` 独立注入。
- **R3 可靠性链**：`ReliabilityExecutor.as_call()` 构造 `Invocation`，显式调用 9 领域策略的领域方法——`_preflight`（`is_tripped`/`detect`/`check_and_mark`/`acquire`/`permit`）→ `_budgeted_call`（`run_with_deadline`/`run_with_retries`/`run_in_slot`）→ `observe_outcome` → `_apply_recovery`（`Degradation.select`），**无统一角色协议、无槽位列表**。
- 跨调用状态（熔断三态/限流令牌桶/幂等表/降级阶梯）住在领域策略实例上，单次流程进度不进实例（A 类纯函数职责）。
- 降级重路由：`Degradation.select(fault, session_id)`（defenses.py）按会话隔离剔除故障目标并写回 available，选 target 后由执行器 `inv.write_routing_target` 写 typed target 并重跑（上限 `_MAX_REROUTE`）。

**看完能答**：call 装饰器怎么被函数组合装配？可靠性领域策略怎么被执行器显式编排？降级链怎么走、为什么状态在策略实例而非 Program？

## 5. 关键陷阱（读码时最容易误解的地方）

1. **`EffectBatch` 伪 API**：compose 不导出它；真并行靠 `program.py:234/311` 的 `yield batch`（列表）。别照 R12 早期文档的 `EffectBatch(...)` 伪代码读。
2. **par 曾是桩**：旧实现只发一个 `Invoke(port="tool", batch=True)` 并丢弃 items、output 恒 None；R2 文档 `:97` 有"禁止退回假实现"的门禁。现已是 lockstep 真并行。
3. **`_carry_x`/`_as_program` 是死代码**：`program.py:89-142` 定义了却全文件无调用点；真正的 carry 在 `_run_child:127-130` 内联完成。别照 `:11-13` 的注释去找错误的 helper。
4. **ReAct 用 `loop_until` 真自循环**：旧实现的 `loop(cond 恒 False)` 已被替换；现在 `ReAct.compile` 用 `compose.program.loop_until`（回注 tool_calls 驱动下一轮，`done` 判收敛），`max_turns` 作防御上限。别照旧文档误读。
5. **build_call 顺序**：`build_call(base, *, decorators=())` 只收函数式装饰器，按内层先注册顺序组合（无 guards 层）；R3 的包裹顺序则是 Timeout 最内 → Retry 居中 → Bulkhead 最外，`extra_plugins` 变换器最外层（executor.py `_budgeted_call`）。
6. **共享 meta 是降级成败关键**：`executor.py::_as_invocation` 在 ctx 已是 Invocation 时复用，否则用 `CallContext(meta=ctx.meta)` 共享同一 dict——前置写出的 fault/typed target 与网关读取同源，重路由不静默失效。
7. **熔断记数只有一处**：`CircuitBreaker.observe_outcome`（executor.py `_budgeted_call`）单次记数；中心抛异常也记一次失败并原样抛回（不吞异常），交降级链处理。
8. **五角色已彻底删除、无术语残留**：`compose/__init__.py` 无 `AOPContainer`/`CompositeCall` 别名，`chain_roles.py`/`call_chain.py`/`adapters.py` 已物理删除（迁移卡 2026-11-22）；R3 只有领域策略与 `ReliabilityExecutor` 显式编排。
9. **DangerLevel fail-closed**：`dto.py:67-81` 的 `coerce` 对未知值/None 回退 CRITICAL（安全策略），不是 SAFE。
10. **race 不真正 cancel**：`program.py:319-332` 首胜后仅 `pending.clear()` 停止推进，取消语义交 R1 CancellationToken。

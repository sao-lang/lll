## 1. 一句话心智模型

整套框架只做一件事：

> **Runner 反复推动一个 generator（Program），它 yield 出「 Effect（意图）」，Runner 把 Effect 交给 Port 执行，把结果回填给 generator，直到它 return。所有能力模块（模型/工具/记忆/RAG/可靠性/技能）都是挂在 Port 上的实现，它们自己不知道循环的存在。**

记住这三个词就够了：

- **Program**：用户的业务逻辑，是一个 generator，读 State、yield Effect、收结果。
- **Effect**：一个有标签的意图对象，四种：`Invoke`（调 Port）、`Spawn`（派生子 Agent）、`Suspend`（挂起等人）、`Terminate`（结束）。
- **Port**：能力的统一插座，名字有 `llm` / `tool` / `rag` / `memory` / `disclosure` / `mcp` / `skill` / `sandbox` / `human` / `audit`。

一句话分层：**内核只认 Effect 和 callable，零领域知识；领域知识全在 harness 的能力包里，由装配层塞进内核的插槽。**

## 2. 四层架构：谁依赖谁

从里到外四层，依赖方向**恒定为外向里**，反向 import 是被禁止的：

```
① runtime（内核 R1）    State / Effect / Program / Runner / Interpreter / fold
       ↑ 只被依赖，不 import 任何上层
② compose（装配层 R2）  组合算子 / call 装饰器 / dispatch / PortCtx / DTO / 协议目录
       ↑ import runtime
③ archs（内置架构 R12） ReAct / PlanExecute / Router / Graph 等 10 个架构
       ↑ import compose + runtime
④ harness（能力包 R3~R9）context / tools / model / rag / skills / resilience / memory
       ↑ import compose + runtime（彼此间少量横向复用）
```

关键佐证：`src/harness/__init__.py` 的文档串明确写「全部基于 R1 + R2 构建，内核零策略；子包按需引入」。

**为什么这样分层**：换一个模型后端、换一套工具、换一个记忆存储，都不用改内核。内核的`Runner`构造只接受一个 `call` 函数——所有花活（重试、超时、熔断、降级）都是包裹在这个 `call` 外面的纯函数链。

本套文档拆解的 7 个模块全在第④层：

| 模块 | 目录 | 主职责 |
|---|---|---|
| context | `harness/context/` | 上下文组装、压缩、重注入、卸载 |
| tools | `harness/tools/` | 工具注册、danger 路由、披露、MCP |
| model | `harness/model/` | 模型网关、缓存、路由、结构化输出、成本 |
| rag | `harness/rag/` | 检索增强流水线 |
| skills | `harness/skills/` | 技能发现 + 注入检测 |
| resilience | `harness/resilience/` | 可靠性执行器 + 九种防线 |
| memory | `harness/memory/` | 双轴分层长期记忆 |

（另有一个 `archs` 层不在本次拆解范围，它只是「用组合算子拼好的 Program 配方」。）

## 3. 主入口①：Runner 的一次运行

文件：`src/runtime/runner.py`。这是**唯一**的 async IO 编排点。

### 3.1 构造 Runner

`Runner.__init__` 收一个必填参数和六个可选参数：

- `call`：Port 调用函数。**这是唯一的必填项**，装配层把整条增强链包好后塞进来。
- `store`：checkpoint 存储，缺省用内存实现 `InMemoryEventStore`。
- `ctx_factory`：上下文工厂，缺省造 `RuntimeCtx(effect, state, session_id)`。
- `checkpoint_every`：每 N 步落一次快照，**最小强制为 1**（`max(1, ...)`）。
- `max_steps`：单 run 步数硬上限，默认 1000，防死循环。
- `cancellation`：取消令牌。
- `notify`：Lifecycle 通知回调 `(相位名, 只读投影)`，缺省 no-op。

构造时还会初始化三个「按会话索引」的字典：`_runtimes`（执行态）、`_reasons`（结束原因）、`_errors`（错误码），以及 `_child_seq`（子会话序号，按父会话独立递增）。

### 3.2 取消令牌为什么要包一层 holder

`CancellationToken` 对外是 frozen 的（`cancel()` 返回新对象）。但 Runner 构造后拿不到新对象，运行中调用 `cancel()` 就会失效。

解法：Runner 内部持有一个可变的 `_CancellationHolder`，构造时从 token 拷贝初值；`Runner.cancel()` 原地置位 holder；每一步 `step()` 开头读 holder。子 Agent 通过 `_bind` 继承同一个 holder，所以取消能递归传播到整棵树。

### 3.3 run() 的入口判断

`run(session)` 做三件事：

1. **终态幂等**：如果会话末事件已经是 `done` / `error` / `suspended`，直接返回 `_result(session)`，不重复跑。
2. 发两个通知相位：`session_start`、`user_prompt`。
3. 进 `_loop`；如果构造期 Program 违规（`ProgramInvalid`/`ProgramCrashed`），兜底产出 error 事件，不抛穿。

`resume(session, answer)` 是挂起恢复：重建一个新解释器，按事件日志回放（见 3.5），把 `answer` 作为末事件（suspended）的回填值，发 `resumed` 通知，再进 `_loop`。

### 3.4 _loop：反复 step 直到终态

```
for _ in range(max_steps):
    report = await step(session)
    if report.status != "running": break
result = _result(session)
if result.status in (done, error): 发 session_end 通知
return result
```

注意：**挂起（suspended）不算会话结束**，不发 `session_end`——resume 后还会再跑一次 run。

### 3.5 step()：整个内核最核心的函数

一次 step 按固定顺序走 10 步：

**第 0 步 · 取消检查**：holder 已置位 → 追加一条 `cancelled` 事件（step=0、无 effect/result），发 `cancelled` 通知，返回 `StepReport`，**不执行任何 Effect**。

**构造执行态**：`_runtime(session)` 首次调用会造一个 `InterpreterImpl(session.program_factory())` 并回放历史事件。构造失败直接返回 error 报告。

**推进游标**：`step_no = rt.step`，然后 `rt.step += 1`——即使本步失败也推进，保证 `trace_id` 单调。

**第 0 步 · 预算预检**：`state.budgets.exceeded()` 为真 → 强制合成一个 `Terminate`，状态置 done，原因写 `BudgetExceeded.code:超限值`，发 `budget_check` 通知。**这是内核硬强制，Program 无法绕过**。

**第 1 步 · 推进解释器**：`batch = rt.interpreter.send(rt.last_value)`。把 generator 往前推一次，拿到下一批 Effect 或 `DONE`。异常折叠为 error 状态。

**批次分派**（五种情况，顺序判断）：

1. `batch is DONE` → Program 已 return，合成 `Terminate`，原因 `program_returned`，状态 done。
2. 并行度检查 `check_parallel(len(effects))` 超限 → 合成 `Terminate`，原因 `BudgetExceeded:parallel_children`，状态 done。
3. **整批都是 `Terminate`** → 快路径，直接置 done，不调 Port。
4. **整批都是 `Suspend`** → 挂起路径，状态 suspended，原因 `wait_human`，发 `wait_human` 通知（带第一个 Suspend 的 question）。混合批（含可执行 Effect）**不会**被当成挂起吞掉。
5. 常规批 → 给每个 Effect 打 `trace_id`（格式 `<session>:<step 4 位>:<index 2 位>`），为每个 Effect 造 ctx 并注入 `invoke` 回调，然后 `asyncio.gather` 并发执行。

**回填值规则**：`batch.batched=True` 时回填 list（成功的取 `data`，失败的取 Result 对象本身）；单个时回填首个结果的 `data`（失败同样取 Result 本身）。**失败时回填 Result 信封而非 None**，这样 Program 能读到错误信息。

**第 2 步 · 纯函数折叠**：`new_state = fold(state, effects, results, reason)`，赋回 `session.state`，发 `state_fold` 通知。

**第 3 步 · usage 汇总**：从每个 Result 的 usage 里取 `cost_usd`、`prompt_tokens`、`completion_tokens` 求和，写进事件。**字段名是具名常量**（读错会静默丢成本）。

**第 4 步 · 记事件**：构造 `Event`，其中 `seq = len(session.events)`（append-only 逻辑序号）、`ts = step_no`（逻辑时钟，无墙钟，保证确定性），追加到会话日志。

**第 5 步 · checkpoint**：终态总是落盘；运行中按 `checkpoint_every` 节流。

最后返回 `StepReport`（含 step、state、effects、results、status、reason、error、events）。

### 3.6 _execute：单个 Effect 怎么执行

```
Spawn  → 走 _child 递归分支，不进 call
Invoke → 走 call 槽（装配层已包入增强链）
Suspend/Terminate → 在 step 的批次层面已处理，不进这里
```

对 `Invoke(port="tool")`，执行前后会发 `before_tool` / `after_tool` / `tool_error` 通知。异常折叠规则：

- `AgentKitError`（框架异常）→ 用它自己的 `code` 作失败码。
- 其他 `Exception` → 用 `PORT_CRASHED` 失败码，消息带异常类型名。**绝不裸抛穿运行时**。

### 3.7 _child：子 Agent

`Spawn` 会递归创建一个子 Session：

- id 格式：`<父 id>:child:<序号>`。序号按父会话单调递增，读序号和写序号之间没有 `await`，单线程下并发安全。
- 子 state 继承父 state，但 `budgets` 扣掉 1 hop。
- 递归 `run(child)` 跑完整子会话（子会话自己也可以再 Spawn）。
- 子会话的全部事件挂回父会话日志，子 Agent 的轨迹对父可见。
- 返回 `Result.success(子 run 的 output)`。

### 3.8 另外三个入口

- `cancel(reason)`：置位 holder，下一 step 生效。
- `replay(session, initial_state)`：纯函数调用 `replay_events`，从初始 State 逐步 fold 出终态。
- `load(session_id, program_factory)`：从 checkpoint 恢复 Session；checkpoint 不含 generator，所以要传工厂重建。无快照抛 `PortMissing`。

### 3.9 13 个通知相位

Runner 会发这些相位（值定义在 `_Phase` 枚举）：`before_tool`、`after_tool`、`tool_error`、`child_spawn`、`child_done`、`cancelled`、`budget_check`、`wait_human`、`state_fold`、`session_start`、`user_prompt`、`resumed`、`session_end`。

内核**只认这个字符串**，不 import 任何 hooks 模块——新增相位要同步枚举两处。

## 4. 主入口②：Interpreter 怎么驱动 Program

文件：`src/runtime/interpreter.py`。职责边界：**只做确定性推进，不做任何 IO**。

### 4.1 一次 send 的逻辑

`InterpreterImpl.send(value)`：

1. 首次推进走 `next(gen)` 启动 generator，其后走 `gen.send(value)` 回填上次结果。
2. `StopIteration` → 返回 `DONE` 哨兵，表示 Program return 了。
3. 其他异常 → 包成 `ProgramCrashed`，绝不裸抛。
4. yield 出来的是单个合法 Effect（Invoke/Spawn/Suspend/Terminate 四选一）→ 走 `_expand` 后返回 `EffectBatch`。
5. yield 出来的是**非空 list/tuple，且元素全是 Effect** → 逐项展开合并，返回 `EffectBatch(batched=True)`。这是「并行声明」的写法。
6. 其他（含**空列表**）→ 抛 `ProgramInvalid`。注意空列表既不是合法 Effect 批，也不能当 DONE。

### 4.2 batch 展开：`_expand`

一个 `Invoke(batch=True, payload={"calls":[...], ...})` 会被展开成多个独立 Invoke：

- 非 Invoke 或 `batch=False` → 原样返回单个。
- batch 但 `calls` 空 → 退化为单个非 batch Invoke，避免空批次。
- batch 且有 calls → 去掉 `calls` 聚合键，每个 call 生成独立 Invoke，payload 用单值键 `'call'` 承载；`trace_id` 和 `idempotency_key` **原样传给每个子 Effect**（否则批量副作用的幂等红线失效）。

`EffectBatch.batched` 为真时，Runner 回填 list 而非单值。

## 5. 主入口③：装配层 compose 怎么把能力接进来

这一层回答一个问题：**内核只认 `call(effect, ctx) -> Result`，那些能力包怎么变成这个函数？**

### 5.1 三块拼图

`src/compose/` 里最关键的三块：

**`dispatch.py`**：`make_dispatch(ports)` 把「port 名 → 处理函数」的映射变成一个 CallFn。逻辑很短：

- 非 Invoke → 返回 `INVALID_EFFECT`。
- 查不到 port → 返回 `PORT_MISSING`。
- 找到就调 handler，异常折叠为 `PORT_CRASHED`。

**`call.py`**：`build_call(base, decorators)` 把装饰器链包到 dispatch 外面。组合顺序是 base → decorators[0] → ... → decorators[n]，即**先注册的在更外层**。内置四个装饰器：`retry_call`、`timeout`、`danger_route`、`injection_guard`，都是纯函数 `CallFn → CallFn`。

**`tool_layer.py`**：`layer_program(port, payload, output)` 产出一个「外壳 Program」——每次调用返回一个新 generator，内容是 `yield Invoke(port=...)` 然后 `yield Terminate(output=...)`。每个能力包的 `build()` 都用它，让 R1 拿到领域无知的 Program。

### 5.2 组合算子（`compose/program.py`）

10 个 A 类算子在**装配期**做 Program→Program 的纯变换：

- `seq(a,b)`：顺序跑，a 的 output 写进 `x-compose.seq.output` 再跑 b。
- `par(items, join)`：扇出并行，一次 yield Effect 列表走 R1 并行，按 `all`/`any`/`majority` 聚合。多数票平票取首现，确定性。
- `branch(fn, arms, default)`：条件分流，先发一个 `Invoke(port="state", op="read")` 拿 State，再按 key 选 arm。
- `race(items)`：首个 Terminate 胜出，其余不再推进（取消语义交 R1）。
- `loop(body, cond, max_rounds)`：显式循环，轮次写 `x-compose.loop.round`。
- `fallback(p, ladders, refuse)`：按序尝试，全失败走 refuse。
- `gate(p, policy)`：唯一能 yield Suspend 的算子，用于审批/澄清。
- `retry(p, attempts, backoff)`：流程级重放。
- `map_state(lens)` / `map_effect(fn)`：高阶变换，分别改 State 视图和 Effect payload。

**算子间传数据不走 R1 的 fold**：用 `State.scratch` 里 `x-compose.*` 前缀的键，由 `_carry_x` 在算子内部合并。因为 R1 fold 不认识这些键，resume 时靠 `program_factory` 重建即可。

### 5.3 内置架构（`archs/recipes.py`）

10 个架构都是「A 类算子的预设配方」，实现同一个 `Arch` 协议（`name` / `version` / `static_check` / `compile`）：`ToolUse`、`ReAct`、`PlanExecute`、`Reflection`、`Router`、`RouterSkill`、`Supervisor`、`Handoff`、`Blackboard`、`Graph`。

它们内部用 `yield from _run_child(...)` 拦截子 Program 的 Terminate，把子流程的 output 转成返回值，避免提前结束整个 run。多步进度用 `Invoke.payload` 的 `x-arch.*` 扩展键随 Effect 传递——原因和算子一样：架构 Program 拿不到 fold 生成的完整 State，只能从回注值里读。

## 6. 六个模块各自挂在哪

一次完整运行，各模块的接入点如下。这是本套文档的总导航：

```
用户 Program（或某个 Arch 的 compile()）
   │
   ├─ yield Invoke(port="llm") ──────→ ModelGateway.as_call / as_dispatch    [03 model]
   │                                     ├─ 先过 ReliabilityExecutor       [06 resilience]
   │                                     ├─ 路由 / 缓存 / 结构化校验 / 成本
   │                                     └─ 真正的 LLMPort 后端
   │
   ├─ yield Invoke(port="tool") ─────→ ToolRegistry.call                    [02 tools]
   │                                     ├─ danger 四级路由
   │                                     ├─ 沙盒 / 人工审批 / 审计 Port
   │                                     └─ 注入检测（web_fetch）           [05 skills]
   │
   ├─ yield Invoke(port="rag") ──────→ RAGPipeline.query                    [04 rag]
   │                                     └─ 改写→召回→RRF→重排→后处理
   │
   ├─ yield Invoke(port="memory") ───→ ContextMemoryManager                 [01 context]
   │                                     └─ 组装/压缩/重注入/卸载
   │                                     └─ MemoryStore 写入/召回链          [07 MemoryStore]
   │
   ├─ yield Invoke(port="disclosure")→ ToolIndex.disclose                   [02 tools]
   │                                     └─ L1 目录 / L2 schema / L3 技能正文 [05 skills]
   │
   └─ yield Invoke(port="skill") ────→ FileSkillProvider.body               [05 skills]
                                          └─ 正文注入检测 fail-closed
```

**装配动作**：每个能力包都提供 `build()`（产出外壳 Program）和可选 `install(reg)`（把自己持有的 Provider 注册进共用注册表）。例如 `ToolsCapability.install()` 先 flush `@tool` 待注册项，再注册 `tool`/`disclosure`/`mcp`/`skill` 四个 port；`ResilienceCapability.install(core)` 把九种领域策略注入执行器，产出一个可信的 CallFn。

**一句话记住接入方式**：能力包 = 「`build()` 给 Program 壳 + `install()` 给 Port 实现」，内核全程不知道这些包的存在。

## 7. 贯穿全文的 8 个公共概念

这 8 个概念在每一册都会反复出现，先在这里统一讲清。

### 7.1 PortCtx

Port 调用的统一上下文。至少带 `session_id`、`state`、`meta`、`invoke`、`cancellation`、`budget_left` 等字段。`meta` 是具名扩展槽（`x-*` 或约定键），用来传 scope、fault、routing_target 等，不改 DTO 结构。

### 7.2 Result 信封

所有 Port 调用返回 `Result`：成功带 `data` 和 `usage`，失败带 `error`。`error` 有稳定 `code` 和 `retryable` 标记。**异常一律折叠为 Result，不抛穿内核**——这是全框架的统一纪律。

### 7.3 fail-closed（失败即拒绝）

安全类设计的统一原则：依赖缺席、格式非法、检测命中、参数不全，一律**显式拒绝**，不静默放行。例子：高危工具无沙盒直接拒绝；技能正文命中注入直接拒载；降级阶梯末级必须拒答；secret 键名直接拒绝写入；空 tenant 直接报错。

### 7.4 x-* scratch 键

`State.scratch` 里的扩展键，约定以 `x-` 开头（`x-compose.*`、`x-arch.*`）。用于算子/架构跨步传递进度，绕开 R1 fold 的领域无知。

### 7.5 具名常量

代码里所有阈值、错误码、角色名、分隔符都用具名常量，不写裸字符串/裸数字。这样比较的右侧永远是常量名，改一处即全局生效。文档里我会把关键常量的值直接写出来。

### 7.6 可插拔四要素

1. 协议（Protocol）；2. 默认实现；3. 替换入口（构造注入）；4. 履约校验（实现协议 + 具名非空）。每个可插拔点都遵守这四条。

### 7.7 墙钟 / 随机显式注入

内部逻辑不直接读系统时间或调全局随机数，而是通过构造参数 `clock` / `rng` 注入，保证可测试、可回放。例：熔断器的 `clock`、重试的 `rng`、幂等的 `clock`。

### 7.8 异步边界：`_run_sync`

记忆模块和 embedder 有一些同步方法要调异步后端。`_run_sync(coro)` 的逻辑：当前无事件循环 → 直接 `asyncio.run`；已有事件循环 → 开一个单线程池跑 `asyncio.run`，避免「事件循环已在运行」冲突。

## 8. 端到端走一遍：ReAct 调一次工具

把上面的零件串起来，看一次真实的 ReAct 运行：

**装配期**（跑之前一次性完成）：

1. 造 `ToolRegistry`，注册若干 `@tool` 函数（装饰时入 `_PENDING` 列表，`register_pending()` 批量落地）。
2. 造 `ModelGateway`，注入 LLMPort、router、cache、validator、cost_guard。
3. 造 `ReliabilityExecutor`，注入重试/熔断/降级策略，core 设为 `gateway.as_call()`。
4. `make_dispatch({"llm": executor.as_call(), "tool": registry.call, ...})` 得到 base call。
5. `build_call(base, decorators=[...])` 包上装饰器链。
6. `Runner(call=...)` 完成内核装配。
7. `ReAct(tools).compile()` 产出 Program。

**运行期**：

1. `runner.run(session)` → `_loop` → 第一次 `step`。
2. `interpreter.send(None)` 启动 ReAct 的 generator，它 yield 一个 `Invoke(port="llm", payload={messages, tools})`。
3. Runner 打 trace_id、造 ctx、调 `call` → 经装饰器 → dispatch → executor → gateway.complete。
4. gateway：解析后端（路由）→ 查缓存 → 成本预留 → 调 LLMPort → 结构化校验 → 记账 → 写缓存 → 返回 LLMResponse。
5. Runner 把结果包成 Result，回填给 generator（单个取 `data`，即含 `content`/`tool_calls` 的 dict）。
6. ReAct 从回注值读 `tool_calls`，第二次 yield 一个 batch Invoke（port=tool，payload.calls=[...]）。
7. Interpreter 把 batch 展开成多个独立 tool Effect，Runner 并发调用 `ToolRegistry.call`。
8. Registry 按 danger 分级：SAFE 直执行、LOW 审计后执行、HIGH 沙盒、CRITICAL 审批+沙盒。
9. 结果作为 list 回填给 ReAct，它把 tool 消息追加进 messages，进入下一轮 LLM 调用。
10. 没有 tool_calls 时 ReAct yield `Terminate(content)`；Runner 置 done、记事件、落 checkpoint、`_loop` 退出、`_result` 汇总返回。

**整个过程中**：context 模块的组装/压缩在模型调用前后由装配层显式调用；rag 的检索结果作为 context 段注入；memory 在会话提交时 `write_cold` + 压缩 + 重注入；skills 的注入检测在披露正文和 web_fetch 时兜底；resilience 贯穿每次 ModelGateway 调用。

## 9. 细节速记卡

- **内核唯一 IO 点**：只有 Runner 能 await。Interpreter 纯推进，fold 纯函数。
- **取消要 holder**：frozen token 无法在运行中被感知，靠可变 holder + 每步读取。
- **失败回填 Result 本身**：不是 None，Program 要能读到错误信封。
- **空列表 yield 是非法的**：ProgramInvalid，不是 DONE。
- **batch 展开传幂等键**：父 Invoke 的 `idempotency_key` 给每个子 Effect。
- **并行度是内核硬预算**：`check_parallel` 超限直接 Terminate，Program 绕不过。
- **Terminate/Suspend 必须整批**：混合批不会被当快路径吞掉。
- **终态总落 checkpoint**，运行中的 checkpoint 最小间隔强制为 1 步。
- **挂起不算结束**：不发 session_end，resume 后继续。
- **子会话 id**：`<父>:child:<序号>`，序号按父会话独立递增。
- **子 Agent 扣 1 hop**：继承父 state 但 budgets.hops -1。
- **架构/算子进度走 x-\* 键**：因为 Program 拿不到 fold 后的完整 State。
- **依赖方向**：harness → compose → runtime，反向 import 是设计违规。
- **一切异常折叠为 Result**：`PORT_CRASHED` / `PROGRAM_CRASHED` 是兜底码。
- **具名常量 > 裸字面量**：比较右侧必须是常量名。
- **fail-closed 是默认**：缺席、非法、命中，一律拒绝而非放行。

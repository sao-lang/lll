# 模块接线现状：R1~R4 如何连接（2026-11-17 实证）

> 本文回答一个问题：**已实现的 R1/R2/R3/R4 之间到底接上没有、缺什么、按设计谁负责接。**
> 结论基于对 `src/` 全量 grep + 测试/demo 调用链的实证，不凭设计文档推断。
> 当前决定（用户 2026-11-17）：**暂不接，保持各模块独立闭环**，本文仅作现状记录。

---

## 1. 一句话结论

**接口全部留好，但没有总装。** R1↔R2 在代码层半接通；R3 的挂载入口已实现但生产代码无人调用；
R4 的网关签名与 R1 的 `call` 不匹配、完全没有进入执行路径。
把各层串成可运行 Agent 是 **R12（装配器）+ R13（组合式装配）** 的职责，而这两个模块目前只有设计文档、没有代码。

---

## 2. 三条接线各自的真实状态

| 接线 | 状态 | 实证证据 |
|------|------|----------|
| **R1 ↔ R2** | 半接通 | `hooks/bus.py:156 ctx_factory()` 注入 Runner；`runtime/runner.py:299 _bind()` 注入 `ctx.invoke`。但需调用方手写 `Runner(dispatch=…, call=…, ctx_factory=bus.ctx_factory())`——`grep "Runner(" src` **无生产代码命中**，只有 `tests/demos/demo_r*.py` 和 `tests/r2/test_extensibility.py` 手搓过。 |
| **R3 → R2** | 接口就绪、无人调用 | `harness/resilience/capability.py::ResilienceCapability.install(bus)` 已实现；`grep -r "ResilienceCapability" src` 只有 `harness/` 自身导出，唯一全栈调用在 `tests/r3/test_capability.py::test_full_stack_dispatch`。 |
| **R4 → R1** | 断链 | `ModelGateway.complete(request: LLMRequest, ctx: PortCtx) -> LLMResponse`；R1 的 `call` 契约是 `(Effect, ctx) -> Result`。两者**签名不同**，中间缺一个适配器。`grep -r "ModelGateway" src` 无执行路径命中。 |

示意图（实线=已接通，虚线=断链）：

```
        [ R12/R13 组装入口 ]   ← 规划中，src/archs/ 未实现
                 │ 虚线：无人实例化 Runner
                 ▼
   [ R1 Runner ] ⟷ [ R2 HookBus ]     ← 已接通（依赖注入）
          │ 虚线               │ 虚线
  缺 Effect→LLM 适配     需显式 install(bus)
          ▼                   ▼
   [ R4 模型推理 ]      [ R3 可靠性 ]
   ModelGateway 未接 call   install 仅测试调用
```

---

## 3. 为什么这样：这不是遗漏，是排期

设计文档把"用户唯一入口"明确放在 R12：
- `docs/02-模块详设/Agent/R12-内置架构与组合.md`：「Agent 装配器（用户唯一入口）」+ `static_check()` 装配期校验；
  源码包 `src/archs/` + `src/compose/` — **均待实现**。
- `docs/02-模块详设/Agent/R13-可插拔与协议契约.md`：三层插拔 + 组合式装配 API — **待实现**。

所以当前状态是自洽的：R1~R4 每个模块内部闭环、独立可测、各有门禁（各 14/14），
但**没有一个 composition root 负责把它们装配成可运行的 Agent**。

---

## 4. 要接起来，具体缺什么

一个最小 composition root 需要三件事（按依赖顺序）：

1. **R1↔R2 的现成组装函数**：把 `bus.ctx_factory()` + `bus.emit` 作为 dispatch 打包，
   免去调用方手写 `Runner(dispatch=…, call=…, ctx_factory=…)`。
2. **R3 的自动挂载**：在组装函数里调用 `ResilienceCapability.install(bus)` 并 `bus.freeze()`。
3. **R4 的 `call` 适配器**：实现 R1 的 `CallFn` 契约 `(Effect, ctx) -> Result`，
   内部把 `Effect(kind=LLM, payload)` 翻译成 `LLMRequest`、调 `ModelGateway.complete()`、
   再把 `LLMResponse` 包成 `Result.success(data=response.model_dump(), usage=…)`。
   这是目前**唯一真正缺代码**的一环——其余两环已有现成函数，只是没被串起来。

补完后，一条端到端用例应能验证：`Program yield Effect(LLM) → bus(before_invoke) → R3 插件 → R4 网关 → Result 回填 → Program 继续`。

---

## 5. 当前可运行的"接线样例"（测试内手搓，非生产入口）

如果你想现在就看到 R3 全栈跑通，唯一的现成例子在
`tests/r3/test_capability.py::test_full_stack_dispatch`：
它手搓了 `Runner + HookBus + ResilienceCapability`，但 `call` 用的是 `fake_invoke`，没接 R4。

```python
bus = HookBus()
ResilienceCapability().install(bus)   # R3 挂载
bus.freeze()

async def dispatch(effect, ctx):
    return await bus.emit("before_invoke", ctx)   # R2 分发

runner = Runner(dispatch=dispatch, call=fake_invoke, ctx_factory=bus.ctx_factory())
```

把 `fake_invoke` 换成第 4 节的 R4 适配器，就是完整的 R1→R2→R3→R4 链路。

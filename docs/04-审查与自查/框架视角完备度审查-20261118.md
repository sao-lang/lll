## 2. 对比《能力域全景》169 项：框架视角下的真实缺口

能力域全景是**能力清单**，但它是从"功能域（A~R）"组织的，不是从"框架抽象"组织的。框架视角下发现：

### 2.1 清单里根本没有的框架核心概念（关键词实证 = 0）

| 概念 | 命中数 | 说明 |
|---|---|---|
| 状态图 / 子图 / reducer / 依赖注入（框架级） | 0 | 虽有 Graph 架构（R12:223-242），但能力域全景未把"图编排/状态合并"列为独立能力项 |
| 条件边（conditional edge） | 1 | R12 有，能力域无 |
| 线程隔离 / 会话并发 | 0 | O6 会话管理标"部分"，无线程级隔离定义 |
| OpenTelemetry / OTLP | 0 | profile 里提"OTel"字样，无规范 |
| 函数调用（function calling）形态 | 0 | 有 ToolPort.call，但"模型原生 function calling 协议"未定义 |
| 输出解析（output parser） | 0 | 有结构化校验，但无"通用 output parser"抽象 |
| 提示模板（prompt template） | 0 | F2 提"Prompt 管理"标部分，无模板语法定义 |

### 2.2 这些缺口为什么重要（框架用户视角）

框架的用户是**开发者**。开发者选框架看的是：
- "我能不能像 LangGraph 那样声明状态图、自定义 reducer？" → 本项目 fold 是固定逻辑，不可扩展（F2 缺口）；
- "我能不能像 PydanticAI 那样一个 decorator 定义工具？" → 只有 ToolPort 协议，无 `@tool`（F5 缺口）；
- "流式能不能拿到工具调用事件？" → 只有 str（F8 缺口）；
- "能不能 OTel 接入现有监控？" → 只有 TelemetryPort 协议，无 OTel 规范（能力域缺口）。

## 5. 与上一轮（产品视角）的差异

上一轮列了"多模态/定时调度/Artifact"等产品功能缺口——从框架视角看，这些**多数属于应用层职责**（框架提供扩展点即可，不必内置）：
- 多模态：框架只需让 `content` 支持结构化 part（F8 关联的 DTO 设计），不必内置图像识别；
- 定时调度：框架提供入口契约（Q8），cron 实现属部署层；
- Artifact：框架提供 StorePort，呈现属应用层。

**框架视角真正的缺口**是 F2（reducer 可扩展）、F3（图编排代码）、F5/F6/F10/F12（默认实现）、F8（流式事件模型）——这些是"框架用户直接依赖的抽象"，比产品功能更根本。

# 多轮迭代仍不完整的根因分析（2026-11-18）

> 触发：用户连续多轮指出"设计/代码还是不完整"，并要求：① 删除阻止修改的门禁（已完成，见 §4）
> ② 检查**为什么经过很多轮还是没有补充完整**（本文回答）。
> 方法：基于 git 提交历史、三层对齐报告的 169 项审计数据、门禁机制的实证分析，不靠感觉。

## 1. 先给结论：五个根因，按影响从大到小

| # | 根因 | 证据 | 后果 |
|---|---|---|---|
| 1 | **工作方式错：响应单点质疑 → 局部补丁，没有全局清单驱动** | 最近 10 个提交中 5 个是纯文档（b0344ca/4c3950f/bfb0235/4251e93/…）；每次都是"用户问一个问题 → 我查 → 我改一处" | 补了 A 处漏 B 处，永远在追尾巴 |
| 2 | **设计层本身不完整，代码无法照着写完整** | 三层对齐报告：169 项中设计充分仅 115、薄弱 46、缺失 8；46 项只有功能名无签名/参数/算法 | 即便动手写代码，也会写出薄实现（ChatMessage 只有 2 字段就是典型） |
| 3 | **"部分实现"被当成"已实现"计数，掩盖了缺口** | C1 多 Provider 接入 = 只有 LLMPort 协议签名就算"已实现"；C7 流式 = 只有 fake 也算 | 审计报表好看，实际能力不可用 |
| 4 | **G5 契约锁（已删）制造了"改代码比改文档贵"的激励** | 每次改公共 API 要 update 基线 + [CONTRACT]/[BREAKING] 评审 + 文档锚点不能动；git 历史里我多次选择"只改文档表述澄清"而非真删薄实现 | 面对 ChatMessage 两字段、Port 无默认实现这类问题，第一反应是加文档说明，不是改代码 |
| 5 | **没有"完成"的客观定义** | 项目没有一份"169 项 → 逐项当前状态 → 下一动作 → 负责人/模块"的活清单；三层对齐报告是快照，§6.1 只追踪了 6 项 | 无法回答"到底还差多少、什么时候算完成" |

## 2. 证据细节

### 2.1 提交历史模式（根因 1）

```
3512e09 docs=1 src=5 tests=4   ← 修 14 项矛盾 + 补 A5/C7 代码（唯一一次系统性的）
b0344ca docs=1 src=0 tests=0   ← 纯文档：三层对齐报告
4c3950f docs=1 src=0 tests=0   ← 纯文档：设计完整性自查
bfb0235 docs=1 src=0 tests=0   ← 纯文档：流式输出设计
ed747f9 docs=0 src=2 tests=6   ← 代码：fake 移出 src
64646fb docs=0 src=12 tests=0  ← 纯格式化（IDE）
4251e93 docs=1 src=0 tests=0   ← 纯文档：接线现状
3d7b8e9 docs=0 src=12 tests=2  ← 代码：编码规则合规重构
417d481 docs=1 src=8 tests=13  ← 代码：R4 实现（唯一真正从零的模块）
a6bc4f8 docs=0 src=8 tests=11  ← 代码：R3 实现
```

模式很清楚：**只有用户点名某个模块"从零做"时（R3/R4）才有大块代码；其余轮次都是用户质疑→我调查→我写报告/改局部**。这不是能力问题，是工作方式问题。

### 2.2 设计层缺口（根因 2）

三层对齐报告 §2 的判定：设计充分 115 / 薄弱 46 / 缺失 8。薄弱项的典型形态：
- `ToolRegistry` 的方法签名写成 `def register(...)`（无参数）——照这个写代码只能猜；
- R9 审批流只写"挂起→审批→resume"，无状态机；
- R4 流式此前只有 `stream()` 一行签名，没有编排设计（已在 3512e09 补 §4.1）。

在这些设计上写出的代码必然是薄实现——**ChatMessage 两字段就是我在设计不足处自己造的"最小可用"结构**，而框架已有四字段的 `runtime.Message`（role/content/name/tool_calls）。这是我没照设计、自己拍脑袋的结果。

### 2.3 "部分实现"被算成"已实现"（根因 3）

三层对齐报告 §3：代码已实现 33 / 部分 61 / 未实现 75。但 33 项里：
- C1"多 Provider 接入"实际只有 `LLMPort` 协议签名 + 网关注入机制，**零个真实适配器实现**（13 个 Port 的默认实现数 = 0）；
- C7 流式此前只有 fake 的 `yield`；
- A5 取消传播此前是空白（3512e09 才补）。

所以"33 项已实现"里有相当比例是"契约就位 + 行为缺失"。这类计数让我在汇报时说"已实现 R1~R4"，但用户实际使用时处处碰壁。

### 2.4 G5 契约锁的激励扭曲（根因 4，已删除）

G5（contract_lock.py）的两个机制：
1. **公共契约哈希锁**：新增/删除/改公共字段 → check 失败 → 必须 update + 评审 + commit 标 [CONTRACT]/[BREAKING]；
2. **文档锚点硬锁**：总设计必须保留"10 内置架构"、禁止"11 内置架构"等 token。

客观效果：改代码（尤其删薄实现）的成本远高于改文档表述。实证：
- 用户问"Port 为什么没默认实现"→ 我在 R2 §1 加了一段"默认由 R3~R11 提供"的澄清文字，**但没有写任何默认实现类**；
- 用户问"ChatMessage 为什么两字段"→ 我上一轮只提议修，没有动手。

G5 已于本轮按用户要求**彻底删除**（contract_lock.py/json、gate_check 的 g5()、Makefile 目标、设计稳定性门禁文档、全文档引用），门禁从 14/14 降为 13/13。将来公共 API 可以自由增改，不必再走评审。

### 2.5 没有"完成"的客观定义（根因 5）

三层对齐报告是 2026-11-17 的快照：169 项、设计 115/46/8、代码 33/61/75。§6.1 补齐进度只追踪了 6 项，其余 163 项没有逐项状态。没有这样的活清单，就不可能知道"补完了没有"。

---

## 3. 为什么"每次检查都发现不完整"——一句话总结

**因为检查的是"能力清单 vs 设计 vs 代码"的全集，而每次修的只是用户当前指出的那一处。**
只要没有一份逐项闭环的清单（根因 5）、设计仍有 54 项薄弱或缺失（根因 2）、且"部分实现"继续被算作完成（根因 3），
那么任何一次全量检查都必然再次发现缺口——这与我是否认真无关，是流程结构决定的。

## 5. 建议：怎么才能真正"补完整"（不在本轮执行，供决策）

1. **建一份活清单**：把三层对齐报告的 169 项拆成逐项状态表（设计状态/代码状态/下一动作/所属模块），每轮结束更新；只有全表绿才算完成。
2. **消灭"部分实现算完成"**：把 C1/C7/A5 这类"只有契约无行为"的项从"已实现"改判为"部分"，直到真后端/真编排落地。
3. **按模块整块推进，不按质疑点推进**：R5（工具）→ R7（上下文记忆）→ R6（RAG）每次完成一个模块的 100% 项，而不是跨模块修单点。
4. **设计先行**：动 R5~R13 代码前，先把该模块设计薄弱项（ToolRegistry 签名、审批状态机等）补到可写代码深度。

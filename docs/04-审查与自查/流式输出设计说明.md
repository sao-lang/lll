# 流式输出：按设计应该怎么做（2026-11-17）

> 回答一个问题：设计文档说 R4 要做流式，框架里到底怎么接、现在缺什么、取消怎么传。
> 基于 `AGENT-总设计` §R4、`R2/R4 模块详设`、`能力域全景 C7`、`Agent应用架构清单` 实证整理。
> 本文只说明方案，不改代码（沿用"暂不接线"的决定）。

---

## 1. 设计怎么定的：流式是 Port 层契约，不是 Effect

关键点：**R1 的 `EffectKind` 里没有 `STREAM`**（只有 llm/tool/child/skill/wait_human/end，
见总设计 §4.2）。流式不在"程序→内核"这一侧，而在"内核→外部模型"这一侧：

```python
# R2/R4 已定义的协议（src/hooks/protocols.py）
class LLMPort(Protocol):
    async def complete(self, req: LLMRequest, ctx: PortCtx) -> LLMResponse: ...
    last_usage: Usage | None   # 流式结算口，后端末块后写入
    def stream(self, req: LLMRequest, ctx: PortCtx) -> AsyncIterator[str]: ...  # PEP525 签名
```

也就是说，设计把一次 LLM 调用拆成两条并列路径：

| 路径 | 返回 | 谁用 | 特点 |
|---|---|---|---|
| `complete()` | 一个 `LLMResponse`（含 content/tool_calls/usage） | R1 的 `Effect(llm)` 走 `call` → `Result` | 一次性、可缓存、可结构化校验、可计成本 |
| `stream()` | `AsyncIterator[str]` 逐块产出 | 面向用户的流式输出通道 | 逐 token、可中断、**不经过 Effect 循环** |

`能力域全景 C7` 对流式输出的定义是「`stream()` 逐 token + 工具事件 + 取消传播」，归属 L1/Port。
所以流式是**LLMPort 实现的责任**——框架只定签名，真后端注入方实现。

---

## 2. 按设计的完整链路（流式请求）

R4 流程图（§3）里的 `LLMPort.complete/stream` 是同一个决策节点。流式路径应该是：

```
用户发起流式请求
    │
    ├─ 路由 ModelRouter 选模型（复用 R4，决策进 trace）
    ├─ 降级矩阵 primary→fallback（复用 R3 Degradation）
    ├─ （可选）精确/语义缓存：命中则直接逐块吐缓存内容，trace=cache_hit
    ▼
LLMPort.stream(req, ctx) → AsyncIterator[str]      ← 注入方实现，框架不内置
    │ 逐块 yield
    ├─ 每块经由 after_model hook 广播（可选，供 UI 订阅）
    ├─ 累计 usage → CostAttributor 记账（流结束或取消时结算）
    ▼
前端逐块渲染；用户点"停止" → 取消传播 → 后端断开 SSE
```

注意：这条链路**绕过了 R1 的 Effect 循环**——它没有 `yield Effect`、没有 `Result` 回填、没有 State fold。
这是设计的刻意选择：`Effect` 是"一次请求换一次结果"的同步抽象，天然不适合逐 token；
流式作为 Port 直连通道，属于 R4 对外能力，不塞进内核执行模型。

---

## 3. 取消传播（设计明确要求）

`Agent应用架构清单` 把「超时与取消语义」列为最常缺失的能力之一，明确包含「流式输出的 cancellation 传播」。
在 Python 里这件事由 `async generator` 语义天然承担：

- 消费方停止迭代或调 `agen.aclose()` → 生成器收到 `GeneratorExit` → 后端连接可 finally 关闭；
- 注入方实现 `stream()` 时，必须在 `try/finally` 里关闭 HTTP 流，否则连接泄漏；
- 成本归因应在结算点处理：流正常结束按实际 usage 记账，用户中途取消按已产出 token 记账（或按后端账单）。

`tests/r4/test_adapter.py::test_stream_cancellable` 已经验证了这个语义（消费一块后 `aclose()` 不阻塞）。

---

## 4. 当前实现状态：契约齐了，真后端和编排是缺口

| 环节 | 状态 |
|---|---|
| `LLMPort.stream()` 协议签名 | ✅ 已定义（`src/hooks/protocols.py`） |
| 测试 fake 的 `stream()` 逐块产出 + 可中断 | ✅ 已验证（`tests/r4/fakes.py` + `test_adapter.py`） |
| `ModelGateway` 有无 `stream()` 编排方法 | ❌ **没有**——目前只有 `complete()`（缓存→路由→调用→校验→记账） |
| 真实后端 OpenAI-compat `stream()` | ❌ 没有，按设计由注入方提供（R4 §6 默认列 OpenAI-compat） |
| 流式走 before_model/after_model hook | ❌ 未接（事件已定义：`LifecycleEvent.BEFORE_MODEL/AFTER_MODEL`） |
| 取消时成本结算 | ❌ 未接 |

所以准确说法是：**协议层完全支持流式，但 R4 网关没有把流式串成编排**，也没有真后端——
这跟"R1~R4 还没总装"是同一个层面的缺口（见《模块接线现状-R1-R4.md》）。

---

## 5. 如果要补齐，最小改动是什么（不阻塞总装）

1. **给 `ModelGateway` 加 `stream()` 方法**：镜像 `complete()` 的前半段（缓存 key/路由/降级），
   但把"调 `llm.complete` + 结构化校验 + 一次性记账"换成"逐块转发 `llm.stream` + 结束时结算"。
   注意：结构化校验无法对不完整流做，所以流式路径下 `StructuredOutputSpec` 要么禁用、
   要么改为"先流式输出、结束时对完整文本校验并按需纠错"（后者复杂，属于增强）。
2. **写一个真后端示例** `src/ports/adapters/llm.py`（设计文档 R4 头部预留的位置）：
   用 httpx 的 `stream="data:..."` 解析 SSE，`async for line in resp.aiter_lines()`，
   `yield` 每个 delta 的 content；`try/finally` 里 `await resp.aclose()` 保证取消不断连。
   这是注入方实现的参考，不属于 R4 核心。
3. **（可选）after_model hook 广播每块**：让 UI/审计订阅；但逐块触发 hook 有性能成本，
   设计上更可能由外层 EventStream（L3）承担，而非 HookBus。

---

## 6. 一句话总结

按设计，流式是 **LLMPort 的 `stream()` 契约**（Port 层），绕开 R1 的 Effect 循环直连模型；
取消靠 async generator 的 `aclose()` 传播；框架负责路由/降级/hook 挂点，真后端由注入方实现。
当前协议和测试 fake 都齐了，缺的是 `ModelGateway.stream()` 编排和一个真实的 SSE 适配器示例。

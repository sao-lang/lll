# 架构契约 · 接线审计清单

> 项目特化 reference（可从本项目 R1–R5 架构中泛化）。专治 AI 写代码时最常见的隐性失败：
> **"模块内部自洽可测，但没人调用/装配，形成功能断点"**。
> S4 自省的必查清单；每条需拿"文件:行号"或调用链证据，拿不出不得标完成。

## 1. 接线审计四问（每个模块实现后逐条问）

1. **谁调用它？** — 模块提供的 public API / port，生产代码里有没有真实调用者？
   - 反模式：只有 `install()` / `register()` 定义，全仓零调用。
   - 检查：`grep -rn "\.install(" src/` 有定义无调用即断点。
2. **它调用谁？** — 模块依赖的下游 port / 适配器，是否真的注入并接上？
   - 反模式：构造参数有 `xxx: Port | None = None`，但运行期恒为 None 走降级。
3. **信号/意图被谁消费？** — emit 出去的 Signal / Decision / Event，有没有订阅者？
   - 反模式：hook 只有枚举常量，零 emit / 零消费。
4. **数据流闭环吗？** — 上游产物（如 tool_calls、degrade_target）有没有下游消费者？
   - 反模式：字段全仓无赋值 / 无读取（如 `tools_catalog` 恒 None）。

## 2. 通用断点模式清单（逐项核对）

| 断点模式 | 症状 | 检查方法 |
|---|---|---|
| 装配层缺失 | 各模块单测全绿，端到端跑不通 | 找 composition root：是否存在统一装配入口？ |
| 门面无后端 | 只有 Protocol + Manager，调用即失败 | 查默认实现类是否存在（非 tests 下的 fake） |
| fake 冒充实现 | 测试绿但生产路径零实现 | 生产代码里 `Fake`/`Stub`/`Mock` 类 = 红线 |
| 协议漂移 | 文档与代码签名不一致 | 对着协议定义逐方法核对签名 |
| 字段空转 | 字段声明了但从不被赋值/消费 | `grep -rn "字段名" src/` 看读写两侧 |
| 触发者缺位 | hook / 事件定义了但无人触发 | `grep -rn "emit\|hook(" src/` 看触发点 |

## 3. 分层契约（按职责隔离，不越界伪造）

- **内核层**：只做编排与纯计算，不 import 上层策略；用结构化投影/鸭子协议解耦（如 R1 不 import R2）。
- **插件层**：只实现 `apply(host)` 挂载，跨调用状态由插件实例自身持有，不设独立状态层。
- **能力层**：协议 + 默认实现 + 归属 + install 四要素齐全；缺默认实现须显式登记为"待实现"并注明归属模块。
- **装配层**：用户未注入时注册默认实例；此层缺失时，其余层"接口就绪"不等于"系统可用"。

## 4. 完成纪律（判定"真的接通"）

1. 拿不出 `文件:行号` 证据的条目一律不得标完成。
2. fake 不算默认实现；门面不算默认实现；test 绿不等于设计兑现。
3. 跨模块归属的缺口只登记不虚标（本模块只负责自己那份）。
4. 每个模块完成后做四向反核对：职责逐行 / 四要素 / 验证矩阵 / 装配归属。

## 5. 使用方式

- 实现每个模块后：跑 `scan_gaps.py` 生成草稿 → 按本清单四问逐条核实 → 结果写入 overview。
- 拷问代码场景：本清单是"功能断点"专项检查的权威依据。
- 与新设计/补充设计相关的重构：先列出新旧契约差异，再逐条核对接线（见 scenarios 场景 9）。

# 场景路由判定（规划器）

> S1 使用。**核心认知：路由不是"匹配场景"，是"规划执行图"。**
> 用户一句话描述的是**执行计划**（节点=场景，边=链/分支，执行模式=路径），不是单个标签。
> 分工：**有限的结构算子用规则匹配**（§1.5，稳定可枚举）；**无限的业务语义交给语义理解**（§2，LLM 擅长）。
> 不确定性靠"假设明示 + 置信度 + 可纠正"兜底；失败降级到只读，绝不猜改码场景。

## 1. 判定流程（五层管线）

| 层 | 做什么 | 规则 |
|---|---|---|
| 层 1 | 结构抽取 | 识别有限算子（§1.5）→ 计划拓扑（单节点/链/分支/并行） |
| 层 2 | 原子意图 | 每个节点用语义三问（§2）定场景 + 路径 |
| 层 3 | 计划构建 | 用场景 I/O 契约（scenarios.md 各场景）校验节点衔接，不符则停下问 |
| 层 4 | 不确定性 | 输出置信度 + 假设[] + 待澄清[]，假设必须明示让用户可否决 |
| 层 5 | 确认闸门 | 高执行 / 中确认 / 低问；执行中每节点完成重新评估后续是否仍适用（重规划） |
| 前置 | 显式场景名 | 用户直接点名场景 → 最高优先，跳过规划 |

## 1.5 结构算子表（唯一需要枚举的东西）

业务词汇无限，但表达**意图结构**的词极少且稳定。只枚举这些算子来决定计划拓扑；业务语义一律走 §2 语义理解。

| 算子 | 信号（有限、稳定） | 计划拓扑 | 处理 |
|---|---|---|---|
| 顺序 | 先 / 然后 / 再 / 接着 / 之后 | 链 A→B→C | 逐段建节点，前段产出喂后段（I/O 契约校验） |
| 条件 | 的话 / 如果 / 要是 / 否则 / 不行就 | 分支 cond? B : skip | 条件节点在条件成立后再定场景（依赖前段产出） |
| 否定 | 不要 / 只 / 别 / 不用 | 排除 | 从候选场景里排除被否定的路径 |
| 并行 | 同时 / 分别 / 都 / 两个都 | 多实例 | 同一场景作用多个对象，或并列多场景 |
| 回指 | 它 / 这个 / 上面那个 / 刚才的 | 上下文依赖 | 读 overview/handoff 消解，消解不了则问 |

> 无算子 = 单节点计划（最常见）。算子组合（如"先…如果…然后…"）= 复合计划，按出现顺序叠加。
> 匹配算子靠语义（"完了再说"也是顺序），不靠字面词表——此表是锚点非穷举。

## 2. 语义三问（核心判定法，替代关键词）

对用户的任何说法，回答三个抽象问题——**答案与具体措辞无关**：

1. **想要什么产出物？**（决定路径）
   - 问题清单 / 代码地图 / 根因台账 / 评估报告 → 只读路径
   - 可运行代码 / 功能 → 改码路径
   - 同步后的文档 → 文档路径
   - 门禁报告 / 覆盖率数字 → 验证路径
2. **动作作用在什么对象上？**（决定场景族）
   - 设计方案 → 场景 2/3/9；代码结构 → 7/10；具体功能 → 4/5/6；故障 → 8；文档 → 11；测试 → 13；交付 → 12
3. **有没有时序结构？**（决定场景链，见 §3.5）
   - 有先后 → 建链，逐段再走前两问。

**泛化示例**（说法不同、三问相同 → 同一场景）：
```
"看看 M4 方案靠不靠谱" / "M4 设计有没有坑" / "帮我审一遍 M4 的设计"
  → 产出物=问题清单, 对象=设计, 无时序 → 场景 9 拷问设计
"这个模块怎么跑的" / "接手这块代码先搞懂" / "理一下调用关系"
  → 产出物=代码地图, 对象=代码结构, 无时序 → 场景 10 代码库理解
```

## 2.1 意图锚点表（语义参考，非穷举逐行匹配）

> 下表是**帮助理解意图的锚点**，不是"出现即命中"的规则。任何说法都先走 §2 语义三问，
> 表只用于交叉验证：语义判出的场景能否在表里找到对应意图族；找不到时**不强行塞入**，提高待澄清置信度。

| 意图族（语义，非字面词） | 上下文条件 | → 场景 |
|---|---|---|
| 从零建立项目骨架 | 代码库为空 | 1 项目初始化 |
| 为系统定架构/分层/选型（产出规格） | 无架构文档 | 2 架构设计 |
| 在既有设计上补未决分支 | 已有设计文档 | 3 补充设计 |
| 新增一个功能（从无到有） | 项目已存在 | 4 项目开发 |
| 调整既有功能（非故障） | 无明确 bug 现象 | 5 项目迭代 |
| 依新/补充设计改代码 | 有新设计输入 | 6 设计驱动重构 |
| 改善代码结构（无新设计） | 只为降复杂度 | 7 项目重构 |
| 排除具体故障 | 有错误现象 | 8 解 bug |
| 评估设计/代码的质量与遗漏（只要结论） | 只读不改 | 9 拷问代码/设计 |
| 搞懂代码结构与调用关系 | 只读理解 | 10 代码库理解 |
| 让文档与代码一致 | 代码变了或文档滞后 | 11 文档同步 |
| 交付前全面检查 | 准备合并/发布 | 12 门禁验收/发布 |
| 为已有代码补测试 | 代码在、测试缺 | 13 测试补课 |
| **以上都不匹配** | — | **提高待澄清，走低置信问用户** |

## 2.2 路径判定（S1 必输出，决定后续阶段）

场景判完后立即判路径。路径决定 S2–S5 哪些阶段进、哪些跳，详见 `scenarios.md` 的"场景 × 阶段矩阵"。

| 路径 | 适用场景 | 后续阶段 |
|---|---|---|
| 改码路径 | 1 初始化、4 开发、5 迭代、6 设计驱动重构、7 重构、8 解 bug | S2→S3→S4→S5 全程 |
| 只读路径 | 9 拷问、10 代码库理解 | S1 → 只读分析 → 写 overview → **结束**（不进 S2/S3/S5） |
| 文档路径 | 2 架构设计、3 补充设计、11 文档同步 | S2(核差异)→S3'(只改文档，不跑代码 TDD)→S4(核签名)→S5 |
| 验证路径 | 12 门禁验收、13 测试补课 | 跳过新功能设计 → S4(全量验证/补测)→S5 |

> 路径判错比场景判错更隐蔽：场景对了但走了改码路径，只读任务会硬跑 TDD 和 verify，空转且误触门禁。

## 3. 上下文消歧（六个高频判据，按语义而非用词）

1. **设计的三种产出**：要架构规格 → 架构设计；要补未决分支 → 补充设计；只要评估意见 → 拷问（9）。看"要的是文档增量还是问题清单"，不看动词。
2. **重构分两种**：带着新设计输入 → 场景 6；只为降复杂度 → 场景 7。看"设计变了没"。
3. **迭代 vs 解 bug**：有明确故障（错误现象/报错栈/行为不符预期）→ 解 bug；只是增强调整 → 迭代。看"是否有故障事实"。
4. **初始化 vs 开发**：看代码库是否已有骨架——AI 应实际 `ls`，不靠词猜。
5. **理解 vs 拷问**：要搞懂结构（产出地图）→ 10；要评估好坏（产出问题清单）→ 9。看产出物，不看"理解/审"用词。
6. **补测试 vs 开发**：代码已在只缺测试 → 13；功能要新建 → 4。看"代码是否已存在"。

消歧用**事实和产出物**说话：查目录、查设计文档是否存在、查是否有新设计输入、查是否有报错栈、查代码是否已存在。禁止仅凭措辞推断；措辞只作语义线索，不作判定依据。

## 3.5 场景链（一句话多个动作）

用户一句话常含**多个有序动作**（"先…然后…""检查…再…""分析完就…"）。此时不是单选场景，而是解析出**有序场景链**，逐段判路径、按顺序执行。

### 切分规则

1. **识别顺序词**：`先 / 然后 / 再 / 接着 / 之后 / 分析完就 / 检查完再` → 多段。
2. **每段独立判场景+路径**：按 §2 判定表逐段解析，各段路径可不同（常见：只读段 → 改码段）。
3. **解析示例**：
   ```
   "先检查 M4 的设计是否完整，然后根据 M4 设计方案写代码"
     段1：检查设计是否完整 → 只读 → 场景 9 拷问设计（产出：设计问题清单）
     段2：根据设计写代码   → 改码 → 场景 6 设计驱动重构
   ```
   另一个例子：
   ```
   "理解一下这个模块，再修掉那个报错"
     段1：理解模块 → 只读 → 场景 10 代码库理解
     段2：修报错   → 改码 → 场景 8 解 bug
   ```

### 链内闸门（关键，否则链式执行无意义）

- **前段产出必须喂给后段**：段1 的产出（设计问题清单 / 代码地图 / 根因）是段2 的输入，段2 不得无视它从零开始。
- **设计闸门**：若段1 是设计类拷问（9）、段2 是"按设计写代码"（6），则**设计问题未解决前禁止进入写代码**。发现致命漏洞应先停下来问用户"设计有问题，是否先补设计？"，而不是硬着头皮按有缺陷的设计写码。
- **只读 → 改码的交接**：段1 只读出口的"清单/地图"必须写入 overview，段2 开始时先读它再动手。

### 无顺序词时

若一句话无顺序词但含多个动词（"检查设计并写代码"），默认按**动词出现顺序**建链；仍判断不清则问用户确认顺序，禁止自行排优先级。

## 4. 结构化路由决策 + 置信度分级（第二、三层防线）

判定结果用**固定结构**输出（可在内部思考，但声明时必须含这些字段）：

```
路由决策（执行计划）：
  拓扑: 单节点 / 链 / 分支 / 并行        ← 由 §1.5 结构算子得出
  节点: [{场景:N, 路径:改码/只读/文档/验证, 输入契约:..., 输出契约:...}, ...]
  边:   [{from:①, to:②, 类型:顺序/条件, 闸门:...}, ...]
  置信度: 0.0~1.0        ← 必填，逼 AI 自查把握
  假设: [<为路由所做且需用户否决的假设>]  ← 没有则写"无"
  依据: <语义三问的答案 + 命中的结构算子，不是"出现了某词">
  待澄清: [<不清楚的点>]   ← 没有则写"无"
```

**假设明示纪律**：若必须做假设才能定场景/路径（如"M5 是设计还是代码"未说），
必须写进 `假设[]` 并请用户否决。悄悄猜对比"明示假设后被否决"更糟——用户没有纠错入口。
例：`假设:["M5 指设计文档（因'靠不靠谱'多用于评设计）；若指代码请说一声"]`。

**置信度分级处理**（置信度决定怎么推进，不是走过场）：

| 置信度 | 处理 |
|---|---|
| 高 ≥0.8 | 按声明直接执行，但仍声明"错了请说" |
| 中 0.5–0.8 | 声明判断 + 依据，**请用户顺手确认**后再推进 |
| 低 <0.5 | **必须提问澄清**，给 2–3 个候选场景让用户选，禁止猜一个往下跑 |

> 置信度不是精确数值，是"我有多确定"的自查。模糊时宁可给低分问用户——问一句的成本远低于跑错一整轮。

## 4.5 路由声明模板（判定后必须先说，用户可纠正）

单场景：
```
我判断本轮走【场景 N：<名称>】，路径【改码/只读/文档/验证】，置信度【X.X】。
依据（语义）：产出物=<...>，对象=<...>，结构算子=<无/顺序/条件/...>。
假设：<为路由所做且需你否决的假设，无则"无">  ← 有假设必须请用户确认
将走的阶段：<S0/S1/... 或"只读分析后结束">；加载 skill：<列表>；脚本：<列表>。
本轮禁止：<禁止项>；下一站：<预期切换>。
如判断有误，请直接说"这是场景 X"或"这是只读路径"，我立即重路由。
```

场景链 / 分支 / 并行（多节点）：
```
我识别到执行计划，拓扑【链/分支/并行】，置信度【X.X】：
  ①【场景 N】路径【...】→ 输出契约：<...>
  ②【场景 M】路径【...】→ 输入契约：<...> ← 校验与①输出匹配
边/闸门：<顺序 or 条件 cond? → 校验通过后才能推进>。
假设：<...>；待澄清：<...>。
若置信度<0.8 或契约不符：请确认计划；闸门未过则停下问用户。
每节点完成后我重新评估后续节点是否仍适用（重规划）。
```

用户纠正（如"不对，这是解 bug"）→ 立即重路由并重声明，不辩解、不沿用错误上下文。这是最终保障——即使语义判断偶尔出错，一句话就能拉回。

## 5. 场景切换与嵌套

- 一个需求常跨场景：架构设计 → 补充设计 → 开发 → 拷问 → 设计驱动重构。
- **每轮会话开始路由一次**；会话内发生阶段跃迁时**重新声明**新场景。
- 每次场景切换写入 overview（场景字段 + 切换原因），便于跨会话续接。
- 拷问场景（9）是只读的：从它产出的"问题清单"是下一场景的输入，不自动执行修复。

- **执行中重规划**：每个节点完成后，重新评估后续节点是否仍适用——若前段产出超出预期
  （如拷问发现目标模块根本不存在、或问题类型变了），停下并重规划剩余节点，禁止硬着头皮按原计划走。
  原因是计划基于路由时的信息，执行中信息会变。

## 6. 判定纪律

1. 猜错场景 = 后面全错；问一句的成本远低于跑错一整轮。
2. 声明不可省略——"未声明不推进"是 S1 的硬出口条件。
3. 用户显式声明 > 一切推断；用户纠正立即生效。
4. 判不出来的信号一律归到"兜底问用户"，不硬塞进某个场景。
5. **失败降级到只读**：匹配不上、置信度低且用户未回应时，降级到场景 9（拷问）或 10（理解）
   ——只读动作危害最小（最多浪费一轮），**绝不猜一个改码场景硬跑**（可能改坏代码）。
6. **假设必须明示**：任何为路由所做的假设写进 `假设[]` 并请用户否决，禁止悄悄假设。
7. **契约不符就停**：链式组合时前段输出契约与后段输入契约不匹配 → 停下问用户，不硬拼。

# 场景路由判定

> S1 使用。场景判错则后面全错，所以路由做成**可判定的三层漏斗 + 一个兜底**，不靠 AI 凭感觉。
> 命中即停，不往下走；三层都不确定则**必须问用户，禁止猜**。

## 1. 三层判定漏斗（按优先级）

| 优先级 | 信号 | 规则 |
|---|---|---|
| 第一优先 | 用户显式声明场景名 | 直接采用，不再判定（如"用架构设计场景""按解 bug 走""进入设计驱动重构"） |
| 第二优先 | 意图动词 + 宾语 | 动词决定意图族，宾语决定具体场景（见 §2 判定表） |
| 第三优先 | 上下文消歧 | 动词有多个候选时，用环境事实收敛（见 §3） |
| 兜底 | 三层都不确定 | 问用户一句，禁止猜一个场景往下跑 |

## 2. 意图判定表（逐行匹配）

| 用户意图信号（动词 + 宾语） | 上下文条件 | → 场景 |
|---|---|---|
| 新建 / 初始化 / 从零搭 + 项目 | 代码库为空 | 1 项目初始化 |
| 设计架构 / 定方案 / 画分层 / 技术选型 | 无架构文档，或明确"做架构设计" | 2 架构设计 |
| 补充 / 细化 / 完善 + 设计 / 方案 | 已有设计文档，只补未决分支 | 3 补充设计 |
| 做 / 开发 / 实现 / 新增 + 功能 | 项目已存在，功能是新的 | 4 项目开发 |
| 改 / 调整 / 增强 + 已有功能 | 无明确 bug 现象 | 5 项目迭代 |
| 按新设计 / 根据补充设计 + 改代码 / 重构 | 有新设计输入 | 6 设计驱动重构 |
| 重构 / 优化结构 / 降复杂度 | 无新设计输入 | 7 项目重构 |
| 修 / 修复 / 报错 / 异常 / 失败 / 不对劲 | 有具体故障现象 | 8 解 bug |
| 审 / 拷问 / 检查漏洞 / 有没有遗漏 / 评估 | 只要结论不改码 | 9 拷问代码 / 设计 |
| 这段代码怎么工作 / 接手陌生模块 / 理解架构 / 摸清调用链 | 只读理解，不要求改 | 10 代码库理解 |
| 补充文档 / 文档与代码不符 / 同步签名到文档 | 代码变了或发现文档滞后 | 11 文档同步 |
| 跑门禁 / 验收 / 准备提交合并发版 | 交付前检查 | 12 门禁验收 / 发布 |
| 给这块补测试 / 覆盖率不够 / 加 characterization test | 代码已存在，只缺测试 | 13 测试补课 |

## 2.5 路径判定（S1 必输出，决定后续阶段）

场景判完后立即判路径。路径决定 S2–S5 哪些阶段进、哪些跳，详见 `scenarios.md` 的"场景 × 阶段矩阵"。

| 路径 | 适用场景 | 后续阶段 |
|---|---|---|
| 改码路径 | 1 初始化、4 开发、5 迭代、6 设计驱动重构、7 重构、8 解 bug | S2→S3→S4→S5 全程 |
| 只读路径 | 9 拷问、10 代码库理解 | S1 → 只读分析 → 写 overview → **结束**（不进 S2/S3/S5） |
| 文档路径 | 2 架构设计、3 补充设计、11 文档同步 | S2(核差异)→S3'(只改文档，不跑代码 TDD)→S4(核签名)→S5 |
| 验证路径 | 12 门禁验收、13 测试补课 | 跳过新功能设计 → S4(全量验证/补测)→S5 |

> 路径判错比场景判错更隐蔽：场景对了但走了改码路径，只读任务会硬跑 TDD 和 verify，空转且误触门禁。

## 3. 上下文消歧（六个高频判错点）

1. **"设计"的三种去向**：搭骨架 → 架构设计；补细节 → 补充设计；只要意见 → 拷问场景。靠动词"做 / 补 / 审"区分。
2. **"重构"分两种**：带新设计输入 → 场景 6；只为降复杂度 → 场景 7。
3. **"改"是迭代还是解 bug**：有明确错误现象 / 报错栈 → 解 bug；只是增强 → 迭代。
4. **初始化 vs 开发**：看目录是否有代码骨架——AI 应实际 `ls` 看一眼，不靠词猜。
5. **"理解" vs "拷问"**：搞懂结构/调用链 → 代码库理解（10）；评估好坏/找漏洞 → 拷问代码（9）。前者产出地图，后者产出问题清单。
6. **"补测试" vs "开发"**：代码已存在只缺测试 → 测试补课（13）；功能本身要新建 → 开发（4）。TDD 在补课场景里只补测试，不写新实现。

消歧用事实说话：查目录、查设计文档是否存在、查是否有新设计输入、查是否有报错栈、查代码是否已存在。禁止仅凭措辞推断。

## 4. 路由声明模板（判定后必须先说，用户可纠正）

```
我判断本轮走【场景 N：<名称>】，路径【改码 / 只读 / 文档 / 验证】。
依据：<命中的信号 / 上下文事实>。
将走的阶段：<S0/S1/... 或"只读分析后结束">。
将加载 skill：<列表>；将执行脚本：<列表>。
本轮禁止：<禁止项>。
下一站：<预期的场景切换>。
如判断有误，请直接说"这是场景 X"或"这是只读路径"，我立即重路由。
```

用户纠正（如"不对，这是解 bug"）→ 立即切换场景并重声明，不辩解、不沿用错误上下文。

## 5. 场景切换与嵌套

- 一个需求常跨场景：架构设计 → 补充设计 → 开发 → 拷问 → 设计驱动重构。
- **每轮会话开始路由一次**；会话内发生阶段跃迁时**重新声明**新场景。
- 每次场景切换写入 overview（场景字段 + 切换原因），便于跨会话续接。
- 拷问场景（9）是只读的：从它产出的"问题清单"是下一场景的输入，不自动执行修复。

## 6. 判定纪律

1. 猜错场景 = 后面全错；问一句的成本远低于跑错一整轮。
2. 声明不可省略——"未声明不推进"是 S1 的硬出口条件。
3. 用户显式声明 > 一切推断；用户纠正立即生效。
4. 判不出来的信号一律归到"兜底问用户"，不硬塞进某个场景。

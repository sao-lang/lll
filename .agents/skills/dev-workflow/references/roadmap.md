## 一、P1 候选场景（🔵 设计中，方案 A 的一部分）

### 场景 10 · 代码库理解（读代码）
- **定位**：当前九场景全是"动手类"，缺"先搞懂"。AI 在陌生代码上直接改 → 制造断点。
- **路径**：只读路径（S0/S1 → 只读分析 → 写 overview → 结束，不进 S2/S3/S5）。
- **加载**：`scan_gaps.py`（摸结构）+ `architecture-contracts.md`（接线四问）+ `code-quality-review`。
- **禁止**：禁止改任何代码；禁止只看单文件下结论。
- **产出**：模块职责 + 调用链 + 断点清单 + 理解笔记 → overview，作为后续场景输入。
- **触发信号**："这段代码怎么工作" / 接手陌生模块 / 要改但不懂 / 理解现有架构。

### 场景 11 · 文档同步
- **定位**：本项目血泪点——`R5-GAP-LIST.md` 的 G07/G13/G15 全是"文档与代码签名不一致""验证矩阵指向不存在文件"。
- **路径**：文档路径（S2 核差异 → S3' 只改文档不跑代码 TDD → S4 核签名 → S5）。
- **加载**：`grill-design`（拷问文档完整性）+ `architecture-contracts`（核契约）。
- **禁止**：禁止只改代码不改文档；禁止"以后再补"。
- **产出**：文档-代码差异清单逐条勾销，拿行号证据。
- **触发信号**：代码签名/契约/行为变了；发现文档与代码不符。

### 场景 12 · 门禁验收 / 发布
- **定位**：项目已有 `tests/tools/gate_check.py`（key=r5，13/13），但工作流无独立"跑门禁"场景，散落在 S5。
- **路径**：验证路径（跳过新功能设计，直接 S4 全量验证 → S5 交付判定）。
- **加载**：`preflight.py` + `verify.py` + `scan_gaps.py` + review skill 全套。
- **出口**：门禁全绿 + 证据入 overview，否则禁止合并/发布。
- **触发信号**：准备提交/合并/发版 / "跑一下门禁" / "验收"。

### 场景 13 · 测试补课
- **定位**：与 TDD 不同——TDD 先写测试再写新实现；测试补课是给**已有代码**加 characterization tests 锁行为。
- **路径**：验证路径（S2 锁行为 → S3' 只补测试 → S4 跑覆盖率 → S5）。
- **加载**：`test-strategy.md`。
- **禁止**：禁止为凑覆盖率写无断言测试；禁止借机改实现行为。
- **触发信号**：现有代码缺测试 / 覆盖率不达标 / "给这块补测试"。

## 二、方案 A · 流程机制增强（🔵 设计中，是激活上述场景的前置）

> 判断：只加场景不改流程，新场景会在 S3/S4 卡死或空跑。必须先修这三处。

### 机制 1 · S1 输出"路径"字段（最关键）
路由时除判场景外，再判路径类型，决定后续阶段：

| 路径 | 适用 | 后续阶段 |
|---|---|---|
| 改码路径 | 开发/迭代/重构/解bug/设计驱动重构 | S2→S3→S4→S5 全程 |
| 只读路径 | 理解/拷问/安全审计 | S1→只读分析→overview→结束 |
| 文档路径 | 文档同步 | S2(核差异)→S3'(只改文档)→S4(核签名)→S5 |
| 验证路径 | 门禁验收/测试补课 | 跳过新功能设计→S4→S5 |

### 机制 2 · 只读出口
S4 自省门禁预设"有代码改动"，只读场景需换出口：产出物 = 发现清单/证据台账，出口 = "清单已交付 + 证据可追溯"而非"测试全绿"。
S4 拆两个变体：改码自省（跑 verify）/ 只读分析（不跑 verify，跑 review）。

### 机制 3 · 场景 × 阶段矩阵
把散落在各场景的裁剪规则收敛成一张统一矩阵，作为 S1 硬输出，AI 查表决定进哪些阶段，不靠临场发挥。

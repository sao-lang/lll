# 样例归纳补全规则（examples → full spec）

> 痛点：用户举例说明需求时，例子往往只是**部分样本**，AI 却只按列举的做，漏掉未列举的同类情况。
> 修改文档/代码时同理——只改明说的那处，不改同类的其他地方。
> 本规则把"从样例归纳出完整意图，再系统补齐"固化成动作，挂在 S1（识别）/ S2（设计）/ S3（实现）/ S4（核对）。

## 1. 核心认知

**用户举例 ≠ 完整需求**。例子是"意图的样本"，不是"清单的穷举"。
AI 的默认错误：把 3 个例子当成 3 条需求，做完这 3 条就认为完成——这是"照字面做"，不是"理解意图"。

正确动作：**归纳样例背后的共同规则 → 推导规则覆盖面 → 补齐未列举的同类项 → 向用户确认**。

## 2. 触发信号（命中任一即启动补全）

1. 用户用"比如 / 例如 / 像…这样 / 举例说 / 至少要包括 / 例如 A、B、C"等措辞。
2. 用户给出 2 个以上具体案例，但未声明"就这些 / 仅此 / 全部"。
3. 用户说"参考 X 那样做""和 Y 类似""按这个模式"，暗示还有同类的没写。
4. 修改类需求中，用户点名"改这里"，但同文件/同模块存在**结构相同的其他位置**。

**反向信号**（不启动或停止补全）：用户明确说"就这些 / 只要这几个 / 不要扩展 / 其他的先不管"——尊重边界。

## 3. 补全四步法（必须按顺序）

### 步骤 1 · 归纳意图（抽象）
从样例中抽出**共同特征与隐含规则**，用一句话表达：
"用户真正要的是 <能力/约束>，样例只是它的 N 个实例。"
例：给了"北京/上海/广州"三个城市 → 意图是"支持城市搜索"，不是"支持这三个城市"。

### 步骤 2 · 推导覆盖面（外推维度）
按下表系统扫一遍，列出样例**之外**应覆盖的维度——这是补全的核心，不能凭感觉：

| 维度 | 要问的问题 |
|---|---|
| 同类枚举 | 还有哪些同类型项没列举？（其他城市/其他状态/其他角色/其他文件） |
| 边界值 | 空、零、最大、最小、超长、特殊字符、首个/末个 |
| 异常路径 | 失败、不存在、无权限、超时、网络错误、重复操作 |
| 变体 | 大小写、别名、不同格式、不同版本、并发/时序 |
| 关联项 | 改这里，谁依赖它？（调用方、契约、文档、测试、配置、索引） |
| 反向 | 什么**不该**匹配/不该改？（排除项、例外、黑名单） |

### 步骤 3 · 分类呈现（先确认，再落地）
把补全结果分三类交给用户，**禁止默默扩大范围**：

```
样例要点：（用户明确给的，直接做）
建议补全：（从规则外推的同类项，建议纳入）
需你确认：（边界/异常等判断项，拿不准的）
```

- 明确属于"完整意图"的（同类枚举、明显关联项）→ 纳入，但在 overview 记录"由样例归纳补全"。
- 涉及行为边界、可能超出意图的（异常策略、反向排除）→ **先问用户，得到确认再做**。
- 用户否决的项 → 从范围移除，不再添加。

### 步骤 4 · 落地后核对
实现/修改完成后，逐条回扫步骤 2 的 6 个维度，确认没有遗漏项被静默跳过；
补充了原样例之外的东西必须在 overview 写明依据（哪条维度推导出来的）。

## 4. 三类场景的补全侧重

### A. 功能设计（场景 1/2/3/4）
- 必查维度：同类枚举、边界值、异常路径、反向排除。
- 产出：设计文档里**显式列一节"样例之外覆盖"**，把补全项和仍需用户决策的假设分开。
- 配合 `grill-design` 对补全项逐条拷问，不留静默假设。

### B. 文档修改（场景 11）
- 必查维度：**关联项**（重点）——同一概念在文档其他章节/其他文档/索引/目录/示例代码中的出现。
- 动作：改一处 → 全文搜同概念 → 列出所有需同步处 → 一次改全，拿行号证据。
- 禁止：只改用户点的那一处，留同概念的其他表述不一致（这正是 G07/G13/G15 类问题）。

### C. 代码修改（场景 5/6/7/8）
- 必查维度：**关联项 + 异常路径**——同名/同模式的实现、调用方、接口契约、测试、错误分支。
- 动作：改一处 → 用 `graphify`/grep 找同类调用与同模式代码 → 判断哪些需要同步改 → 列出确认。
- 配合 `scan_gaps.py` 的断点线索 + `references/04-guards/architecture-contracts.md` 的接线四问核对接线是否完整。
- 禁止：只改被点名的那一处就宣称完成；禁止借"补全"之名夹带设计外的新功能（守住 diff 边界）。

## 5. 纪律（防止走过场）

1. **补全 ≠ 擅自扩大**：区分"完整意图内的同类项"（可直接补，记录依据）和"可能超范围的判断项"（先问）。
2. **禁止假补全**：不能只在回复里说"我还考虑了 XX"，却不落进设计文档/代码/overview。
3. **拿证据**：每补一项，写明从哪个样例、按哪个维度推导出来的（可追溯）。
4. **用户优先**：用户说"就这些"时尊重；用户的否定优先于 AI 的推断。
5. **不替代路由**：本规则是 S1 之后贯穿执行动作的约束，不改变场景判定（见 `references/01-routing/routing.md`）。

## 6. 在 conductor 中的挂载

| 阶段 | 动作 |
|---|---|
| S1 路由后 | 识别触发信号，若命中则在声明中加一句"本轮启用样例补全规则" |
| S2 设计计划 | 走四步法，设计文档含"样例之外覆盖"节；`grill-design` 拷问补全项 |
| S3 实现 | 按补全清单实现，关联项逐条核；同模式代码一并处理（代码场景） |
| S4 自省 | 缺口台账增加一项："样例补全的项是否都落地且有证据？" |
| 文档/改码场景 | 按 §4 B/C 的侧重，全文/全模块搜同类项，列清单确认后改 |

补全记录写入 overview 的"关键决策"一节，格式：`补全项 X — 维度 Y — 从样例 Z 推导 — 已纳入/用户确认/用户否决`。

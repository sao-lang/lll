# 测试驱动开发 TDD（conductor 内置工程纪律）

> 来源致谢：提取自 obra/superpowers 上游的 `test-driven-development/SKILL.md`，本地化重述。

强制 RED-GREEN-REFACTOR 循环。没有"先写实现再补测试"的捷径。

## 循环步骤

1. **RED（红）**：先写一个**描述期望行为**的测试，运行它，确认它失败——且是因为"功能还没实现"而失败，不是因为测试写错。
2. **GREEN（绿）**：写**最少量的代码**让测试通过。不要顺手加测试没要求的特性。
3. **REFACTOR（重构）**：在测试保护下清理重复、命名、结构。重构后测试必须仍绿。
4. **提交**，然后进入下一个循环。

## Verify RED — 看它失败（强制，不可跳过）

跑测试后逐条确认：

- 测试是 **fail（断言失败）**，不是 **error（报错）**——error 要先修到正确失败。
- 失败信息与预期一致。
- 失败**因功能缺失**，不是拼写错误或测试写错。

| 现象 | 处理 |
|---|---|
| 测试直接通过 | 你在测已有行为——**改测试**，不是改实现 |
| 测试报错（error） | 修 error，重跑到"正确失败" |

## Verify GREEN — 看它通过（强制）

- 你写的测试通过。
- **其他测试仍通过**。
- 输出干净（无 error / warning）。

**"其他测试"指整个项目套件，不只是你那个文件。** 单个测试文件绿 ≠ 套件绿。
宣布完成前必须跑项目的测试命令（裸 `pytest` / `npm test` / `cargo test`，看仓库用什么），
即使任务里只点名了一个测试文件——范围声明约束的是**交付物**，不是**验证**。
这次运行暴露的任何失败（包括不是你引起的）都要在报告里点名；
**一个你眼看着红却没提的测试 = 报告因遗漏而失真**。

## 铁律

- **测试前写的业务代码，一律删除**，从测试重新推导实现。
- 不允许"先实现、后补测试"来假绿。
- 一个循环只解决一个行为。

## 最常见的五个借口（对照打回）

| 借口 | 真相 |
|---|---|
| "太简单不用测" | 简单代码也会坏，测试只要 30 秒 |
| "我先实现，之后补测试" | 后补的测试立刻通过＝什么都没证明；你没看过它红，就没证明它能抓 bug |
| "已经手动测过了" | 手动测试无记录、不可重跑、压力下会漏；"试了能用" ≠ 全面 |
| "删掉这几小时可惜" | 沉没成本；真正的选择是"用 TDD 重写（高置信）"还是"留着后补测试（低置信、大概率有 bug）" |
| "精神实质一样，不必拘泥形式" | 后测回答"这做了什么"，先测回答"这该做什么"；后测被已有代码偏见污染 |

> 完整 13 条借口表见上游 `obra/superpowers` 的 `test-driven-development/SKILL.md`；此处保留最致命的 5 条。

## 红旗清单（出现即停下重来）

- 先写代码后写测试 / 测试在实现后补 / 测试立刻通过 / 说不清测试为什么失败 / "就这一次"
- "手动测过了" / "精神实质一样" / "留作参考先适配现有代码" / "TDD 太教条，我更务实"
- 处理：**删除该代码，从 TDD 重新开始。**

## 验证

每个循环结束跑测试套件全绿才算数。计划里的"验证"字段就来自这些测试。

## 与 conductor 测试策略的分工

- 本文件管**怎么执行 TDD 循环**（红→绿→重构的纪律）。
- `references/04-guards/test-strategy.md` 管**测试层级选择**（金字塔/Mock 边界/覆盖率达标口径/假绿识别）。
- 场景 13（测试补课）用 TDD 变体：只补 characterization test 锁现有行为，不写新业务实现。

# 十三场景详细流程

> 每个场景是一段"主控归属 + 加载项 + 禁止项 + 下一步"的明确指令。
> S0（会话开始）与收尾的 overview 写入对所有场景通用。
> **主控统一为 conductor 自己**：下文每个场景写成一条**工程能力链**（如 `brainstorm` → `plan` → `tdd`）。
> 能力是 conductor 内化的工程节点，逐个来源/去向/契约见 `engineering-catalog.md`；
> 方法论详情见 `engineering-{workflow,tdd,debugging,code-review}.md`。
> 能力名是流程节点，不是外部 skill——不再加载任何外部流程 skill。

## 通用前置（所有场景必做）

1. 依赖预检：运行 `python .agents/skills/conductor/scripts/preflight.py --project-root .`，缺失项先解决或显式登记例外。
2. 建 overview：`overviews/YYYY-MM-DD/YYYYMMDD-HHMM-主题.md`（见 `overview.md`）。
3. 读上次 handoff（若有）：定位上次 suggested skills 与未完成项。
4. 场景路由声明：向用户说清"本轮场景 / 加载哪些 skill / 禁止项 / 下一站"。
5. 若识别为**场景链**（多动作，见 routing.md §3.5）：按链声明每段场景+路径+闸门，逐段执行，每段完成单独声明进度。

### 场景链执行纪律

- 前段产出（设计问题清单 / 代码地图 / 根因）写入 overview，后段开始先读取，不得无视。
- 设计闸门：段1 拷问设计（9）、段2 按设计写代码（6）时，设计漏洞未解决**禁止进入写代码**；先问用户是否补设计。
- 只读段结束不自动进入改码段——遇闸门或需用户决策时停下问，得到确认再推进。
- 例："先检查 M4 设计是否完整，然后按设计写代码" = 场景9（只读，产出设计清单）→ 闸门核对 → 场景6（改码，按设计改）。

## 场景 I/O 契约表（链式组合的类型系统）

每个场景是带输入/输出契约的节点。构建执行计划时，用本表校验"前段输出能否喂给后段输入"——
契约不符则停下问用户，不硬拼。这把"设计闸门"从特例规则泛化为契约推导。

| 场景 | 输入契约 | 输出契约 | 路径 |
|---|---|---|---|
| 1 初始化 | 需求 + 技术选型 | 项目骨架 + 设计文档 | 改码 |
| 2 架构设计 | 需求 | 架构文档 + 未决清单 | 文档 |
| 3 补充设计 | 设计文档 + 问题清单/缺口 | 更新后设计文档 | 文档 |
| 4 项目开发 | 规格 + 设计 | 新功能代码 + 测试 | 改码 |
| 5 迭代 | 已有功能 + 变更要求 | 调整后代码 | 改码 |
| 6 设计驱动重构 | 设计文档（须已解决已知问题） | 符合设计的代码改动 | 改码 |
| 7 重构 | 现有代码 + 行为测试 | 等价重构的代码 | 改码 |
| 8 解 bug | 故障现象 + 复现 | 修复 + 回归测试 | 改码 |
| 9 拷问设计/代码 | 设计文档或代码 | **问题清单**（带行号/严重度） | 只读 |
| 10 代码库理解 | 代码库 | **代码地图 + 调用链 + 断点清单** | 只读 |
| 11 文档同步 | 代码签名 + 现有文档 | 同步后文档 + 差异清单 | 文档 |
| 12 门禁验收 | 全量变更 | **门禁报告 + 证据** | 验证 |
| 13 测试补课 | 已有代码（行为已知） | 新增测试 + 覆盖率证据 | 验证 |

**常见合法衔接**（契约匹配）：
- 9 的输出（问题清单）→ 3 的输入（需设计文档+问题清单，设计文档由上下文提供）
- 10 的输出（代码地图）→ 8/7 的背景输入
- 3 的输出（更新设计）→ 6 的输入（设计文档）

**非法衔接示例**（必须停下问）：
- 9 的输出（问题清单）直接喂 6 的输入（要设计文档，不是问题清单）→ 问"是否先把问题清单落实成设计更新（场景3）？"
- 10 的输出（代码地图）喂 12（要全量变更）→ 地图不是变更，问用户意图。

## 场景 1 · 项目初始化

- **工程能力链**：`brainstorm`（需求→设计文档）→ `plan`（设计→实施计划），**到计划为止，不写业务代码**。
- **契约传递**：brainstorm 输出的设计文档直接喂给 plan；plan 输出计划后本场景结束。
- **工具**：brainstorm 阶段调 `grill-design` 拷问技术选型；建 overviews 目录；编码规则文件就位。
- **禁止**：禁止在规格未确认前生成实现代码；禁止引入未选型的依赖。
- **下一站**：用户确认设计 → 进入"项目开发"场景。

## 场景 2 · 架构设计

- **工程能力链**：`brainstorm`（架构版：设计树展开），**止步于架构规格，不写实现代码**——不进 `plan`/`execute`。
- **契约传递**：产出架构文档 + 未决清单，作为后续"补充设计/项目开发"的输入。
- **工具**：`brainstorm` 调 `grill-design` 逐层拷问架构决策（每分支必须有结论、不许静默假设）；加载 `architecture-contracts.md` 作设计约束。
- **产出**：架构文档（分层/模块/契约/数据流/装配入口）+ 未决假设清单（已解决的勾销，未解决的显式登记）。
- **禁止**：禁止在架构未确认前写实现；禁止用"通用框架"掩盖未定的技术选型；禁止遗漏装配层设计（composition root）。
- **下一站**：架构确认 → 进入"补充设计"（细化）或"项目开发"（落地）。

## 场景 3 · 补充设计

- **工程能力链**：局部 `brainstorm`（**只针对缺口分支**），不重开已确认结论——不进 `plan`/`execute`。
- **契约传递**：输入旧设计文档 + 问题清单，输出更新后设计文档（契约与场景 6 的输入匹配）。
- **工具**：先定位已有设计与未决清单 → 只对未决部分用 `grill-design` 拷问 → 增量写入（标注变更点）。
- **产出**：设计补充章节 + 更新后的未决清单（减少）。
- **禁止**：禁止重写/推翻已确认且未宣布变更的设计；禁止静默修改历史结论（必须留变更记录）。
- **下一站**：补充确认 → 若涉及既有代码改动，进入"设计驱动重构"场景。

## 场景 4 · 项目开发

- **工程能力链**（最完整，10 个能力全走）：
  `brainstorm`（需求→设计）→ `worktree`（隔离+基线）→ `plan`（设计→计划）→
  `execute`（计划→任务产出，subagent 两段评审）→ 每个任务内嵌 `tdd`（行为→实现）→
  `review`（产出→分级结论，每任务间）→ `receive-review`（反馈→仍绿）→
  `verify`（声明→证据，S4）→ `review`（终审）→ `finish`（全绿→交付决策）。
- **契约传递**：设计文档→计划→任务产出→评审结论→验证证据→全绿变更，逐级喂给下一能力；任一环断裂停下。
- **工具**：S0 预检 + S4 自省脚本；`execute`/`tdd` 阶段加挂 ponytail + caveman + coding-rules。
- **禁止**：无失败测试不写实现；魔法字符串不具名不提交；S4 未过不进 review。
- **下一站**：全绿后 finish → 写 overview + handoff。

## 场景 5 · 项目迭代

- **工程能力链**：`brainstorm`（轻，确认变更范围）→ `plan`（拆变更任务）→ `tdd`（锁行为+实现）→ `review` → `verify` → `finish`。
- **契约传递**：变更要求→影响面→任务计划→实现→评审→验证证据。
- **工具**：影响面分析（受影响模块 / 调用链 / 契约）；回归检查清单。
- **禁止**：禁止在未列影响面前改动；禁止破坏既有公共契约（除非规格明确要求）。
- **下一站**：回归测试全绿 → review → 收尾。

## 场景 6 · 设计驱动重构（依新设计或补充设计）

- **触发**：用户给出新设计或补充设计，要求据此改现有代码。本场景是"有设计输入的重构"，区别于场景 7 的"无新设计的纯结构优化"。
- **工程能力链**：`plan`（按设计差异拆任务）→ 每条差异用 `tdd` 锁新契约（红）→ 改实现（绿）→
  `review`（逐条核对接线）→ `verify` → `finish`。若接线断裂触发 `debug` 定位。
- **契约传递**：新设计→差异清单→行为测试→实现→接线核对证据。
- **工具**：
  1. 加载 `architecture-contracts.md`，先做**设计差异清单**：逐条列出"新设计 vs 现状"的契约变化（新增/删除/改签名/改数据流）。
  2. 对每条差异，先写"行为测试"锁定新契约（红），再改实现（绿）。
  3. 改完后按差异清单逐条核对接线（谁调用、谁消费、信号有人接），写入 overview。
- **禁止**：
  - 禁止边重构边夹带设计之外的新功能或顺手优化（ponytail 也禁止扩大 diff）。
  - 禁止在无测试保护下改结构；禁止静默偏离设计（偏离必须记理由）。
  - 禁止只改代码不改/核对设计文档（文档与代码必须同步）。
- **下一站**：差异清单逐条勾销 + 全绿 → review → 收尾；若发现新设计本身有漏洞，转"补充设计"场景。

## 场景 7 · 项目重构

- **工程能力链**：`tdd`（先补行为测试锁定等价性）→ 改结构 → `review` → `verify`（行为等价证据）→ `finish`。
- **契约传递**：现有代码+行为测试→等价重构代码→等价性证据。
- **工具**：ponytail 砍复杂度（YAGNI 七级梯）；变更前后行为等价性证据。
- **禁止**：**禁止夹带新功能**；禁止在无测试保护下改结构；禁止扩大 diff 到无关代码。
- **下一站**：行为等价 + 全绿 → review → 收尾。

## 场景 8 · 解 bug

- **工程能力链**：`debug`（4 阶段根因）→ `tdd`（复现测试先红后绿）→ `verify`（原 bug 测试 + 回归）→ `review` → `finish`。
- **契约传递**：故障现象→根因→复现测试→修复→回归证据。
- **工具**：根因台账（现象 / 假设 / 证据 / 结论）；回归证据（复现测试先红后绿）。
- **禁止**：禁止未定位根因就改代码（猜改）；禁止只修表象不加复现测试。
- **下一站**：复现测试转绿 + 无新回归 → review → 收尾。

## 场景 9 · 拷问代码 / 设计（纯只读）

- **工程能力链**：无（本场景不改代码）。
- **本外壳主导**：
  - 拷问设计：加载 `grill-design` / `grill-me`，输出设计树 + 未决假设清单。
  - 拷问代码：加载 `code-quality-review`（七维）+ 缺口台账法（功能遗漏 / 功能断点 / 覆盖盲区）。
- **禁止**：禁止在拷问场景修改任何生产代码；禁止把"发现问题"变成"顺便修了"。
- **下一站**：输出结构化问题清单 → 用户决定是否转入"项目迭代 / 重构 / 解 bug"场景。

## 场景 10 · 代码库理解（纯只读）

- **路径**：只读路径 —— S0/S1 → 只读分析 → 写 overview → **结束**，不进 S2/S3/S5。
- **工程能力链**：无（本场景不改代码）。
- **本外壳主导**：
  1. 加载 `graphify`：若项目已有图，用 `graphify query` 问调用链/影响面/god nodes；若无图且为跨文件大项目，先 `/graphify .` 建图（冷启动有成本，小项目跳过）。
  2. 加载 `architecture-contracts.md` 的接线四问逐模块核。
  3. 跑 `scan_gaps.py` 拿断点线索（弱信号，需核实）。
- **产出**：模块职责 + 调用链 + 断点清单 + 理解笔记 → 写入 overview，供后续场景引用。
- **禁止**：禁止改任何代码；禁止只看单文件下结论；禁止把 graphify 的 INFERRED 边当已验证事实（打开源码核对）。
- **下一站**：理解完成后，用户决定转入"拷问 / 迭代 / 重构 / 解 bug"场景。

## 场景 11 · 文档同步（文档路径）

- **路径**：文档路径 —— S2(核差异) → S3'(只改文档，不跑代码 TDD) → S4(核签名) → S5。
- **工程能力链**：局部 `brainstorm`（只核差异）→ 改文档 → `verify`（核签名，不跑新功能 tdd）。
- **契约传递**：代码签名+现有文档→差异清单→同步后文档。
- **工具**：`grill-design` 拷问文档完整性 + `architecture-contracts` 核契约一致性；差异逐条勾销拿行号证据。
- **禁止**：禁止只改代码不改文档；禁止用"以后再补"敷衍；禁止静默改历史结论（留变更记录）。
- **下一站**：差异清单全部勾销 + 签名核对通过 → S5 收尾。

## 场景 12 · 门禁验收 / 发布（验证路径）

- **路径**：验证路径 —— 跳过新功能设计，S4 全量验证 → S5 交付判定。
- **工程能力链**：无（只验证，不写新代码）。
- **本外壳主导**：`preflight.py` → `verify.py --lang <每个语言>` → `scan_gaps.py` → `code-quality-review` + `metago-code-review-deep`（若项目有 gate_check 脚本一并跑）。
- **出口**：门禁全绿 + 全部证据入 overview，否则**禁止合并/发布**。
- **禁止**：禁止带 Critical/阻塞项收尾；禁止用"测试大概没问题"代替退出码。
- **下一站**：全绿 → 交付（合并/开 PR/保留）→ 写 overview + handoff。

## 场景 13 · 测试补课（验证路径，TDD 变体）

- **路径**：验证路径 —— S2(锁行为) → S3'(只补测试，不写新实现) → S4(跑覆盖率) → S5。
- **工程能力链**：`tdd` 变体——先补 characterization test 锁定现有行为（红），但**不新增业务实现**（绿来自已有代码）→ `verify`（跑覆盖率）。
- **契约传递**：已有代码→行为测试→覆盖率证据。
- **工具**：`test-strategy.md`；按达标口径核对覆盖率与通过率；识别假绿信号。
- **禁止**：禁止为凑覆盖率写无断言测试；禁止借机改实现行为（除非测试暴露真 bug 且用户确认）。
- **下一站**：覆盖率达阈值 + 全绿 → S5 收尾。

## 只读出口（只读路径专用）

只读路径（9 拷问 / 10 理解）的出口条件**不是"测试全绿"**，而是：

- 产出物 = 发现清单 / 代码地图 / 证据台账；
- 出口 = "清单已交付 + 每条带源码位置或证据"；
- S4 走"只读变体"（不跑 verify，因无代码改动可验）。

禁止对只读场景套用"未达标不许进 review"的改码门禁——那会让只读任务空转或误判。

## 缺口台账法（S4 自省专用，市场 skill 不覆盖）

先用脚本生成草稿，再人工逐条核实——脚本给线索，判断归 AI，两者都不省：

```bash
python .agents/skills/conductor/scripts/scan_gaps.py --path src     # 缺口台账草稿
python .agents/skills/conductor/scripts/verify.py --lang <lang>    # 验证命令退出码
```

逐条核对（每项需拿证据：文件:行号 / 测试输出 / 覆盖率），拿不出证据不得标完成：

1. **功能遗漏**：设计文档 / 需求清单的每条承诺，代码里是否有对应实现？（对照 `architecture-contracts.md`）
2. **功能断点**：模块"接口就绪"是否真被装配层调用？（composition root、dispatch/call 接线、hook 触发者——scan_gaps 的 install 无调用者/协议无实现是弱信号线索，需人工确认）
3. **测试覆盖率**：是否达到阈值？按 `test-strategy.md` 的达标口径核对，警惕假绿。
4. **通过率**：测试全绿？有无 flaky / skip / xfail 掩盖？
5. **规则符合**：魔法字符串、注释完整性、类型明确、长度基线——以 `verify.py` 退出码为证据。
6. **安全红线**：按 `security-redlines.md` 核对密钥/注入/危险路由/成本闸门。

台账写入 overview 的"验证结果"一节，失败项列"未完成项与下一步"。

# Review 输出契约与交付闸门

一份 review 有没有用，取决于它能不能**照着改**。这份契约就是为了确保这一点。

---

## 一、输出结构（固定五段）

```
## 结论
一句话：本次改动是否建议合入，以及最主要的 1~2 个原因。

## 阻塞项（Blocker）
[逐条，格式见下]

## 应该改（Should）
[逐条]

## 可选（Nit，最多 3 条）
[逐条]

## 未覆盖
明确说明哪些部分没读到 / 没验证，以及为什么。
```

`## 未覆盖` 不能省。写了「没看测试文件」比不写要好得多 —— 它告诉读者结论的边界在哪。

---

## 二、单条结论的四段格式

```
[Blocker] src/order/service.py:142
现象：库存扣减在事务外执行
为什么重要：扣减失败时订单已提交，会出现超卖；当前日单量下预计每天 X 笔
改法：
    def submit(self, order):
        with self.db.transaction():
            self.orders.insert(order)
            self.stock.deduct(order.items)   # 移进事务
```

四段缺一不可：

| 段 | 缺失后果 |
|---|---|
| 位置 | 用户要自己找，等于没说 |
| 现象 | 读者不知道你在说哪段代码 |
| 为什么重要 | 无法判断优先级，会被当成风格意见忽略 |
| 改法 | 知道有问题但不会改，仍然卡住 |

**没有改法的结论，要么补改法，要么删掉。**

---

## 三、分级规则

| 级别 | 定义 | 数量 |
|---|---|---|
| Blocker | 会出错 / 会丢数据 / 有安全影响 | 不限 |
| Should | 不改会积累成问题，本次不改不炸 | 不限 |
| Nit | 风格与偏好 | **最多 3 条** |

🔴 **Nit 超过 3 条就删到 3 条** —— 挑最有价值的留。满篇 Nit 的 review
会让真正的问题被淹没，这是本技能要避免的头号失败模式。

---

## 四、交付前闸门（逐项自检）

- [ ] 每条结论都有 `文件:行号`
- [ ] 每条结论都有「改法」段（不是「建议优化」，是具体代码）
- [ ] Nit ≤ 3 条
- [ ] 没有把刻意为之的取舍当成缺陷（第 1 步「搞清意图」做实了吗）
- [ ] 没有「建议进一步测试」这类无信息量的结论
- [ ] Blocker 的影响面写清楚了（会导致什么后果，不是「可能有问题」）
- [ ] 性能类结论给了量级估算，或标注「需实测」
- [ ] `## 未覆盖` 段存在且具体

任何一项不通过，回去补，不要交付。

---

## 五、两种必须避免的结论

### 1. 含糊好评

❌ 「整体不错，逻辑清晰，建议合入。」

这一句没有信息量。如果真的没问题，要说清**在哪些维度上做了什么检查**：

✅ 「本次扫描覆盖七维：正确性的边界值清单（空输入/单元素/超长）已逐项过，
错误处理未发现静默吞异常，资源生命周期中两处文件打开均用了上下文管理器。
未发现 Blocker 与 Should。以下 2 条为可选改进。」

### 2. 无位置投诉

❌ 「这里的异常处理不太好。」

✅ `[Should] src/api/client.py:88` + 现象 + 为什么 + 改法。

---

## 六、语气

- 对**代码**下判断，不对人下判断
- 不确定的地方写「未确认」+ 需要什么信息才能确认，不要写成肯定句
- 不给出「没问题」这类结论；只陈述本次检查覆盖了什么

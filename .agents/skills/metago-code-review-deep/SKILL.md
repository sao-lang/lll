# 深度代码审查（metago-code-review-deep）

## 什么时候用我（用户通常这么说）

代码要合并或交付前想被认真挑一遍时用它。你说「帮我审一遍代码」「哪里有安全漏洞」，它按 Critical/Major/Minor/Info 四级出结构化审查报告。

> 本节为 2026-09-25「触发词白话化」改造新增：用用户的原话描述使用场景，提高在对话中被正确调用的命中率。功能与实现未改动。

## 描述
对代码进行多维度分级审查，检测逻辑错误、安全漏洞、性能问题、可维护性缺陷、风格不一致。输出含修复建议和优先级的结构化报告。

## 触发条件
- 用户请求代码审查、PR Review、Code Review 时激活
- 代码提交前审查（pre-commit hook 场景）
- 与 `metago-decision-lock` 协同：开发者任务输出代码时强制触发

## 核心流程

### 1. 静态结构分析
- 文件组织与模块划分是否合理
- 函数/类职责是否单一
- 依赖关系是否清晰（无循环依赖）
- 代码重复度检测（DRY 原则）

### 2. 逻辑正确性审查
- 边界条件处理（空值、极值、越界）
- 异常路径覆盖（错误处理、资源释放）
- 并发安全（竞态条件、死锁）
- 算法正确性（时间复杂度、空间复杂度）

### 3. 安全漏洞审查
- 注入漏洞（SQL/命令/XSS）
- 认证授权缺陷
- 敏感信息泄露（硬编码密钥、日志泄密）
- 依赖漏洞（已知 CVE）

### 4. 性能审查
- 数据库查询效率（N+1、全表扫描）
- 内存泄漏风险
- 不必要的同步阻塞
- 资源未释放（文件句柄、连接池）

### 5. 可维护性审查
- 命名清晰度（变量、函数、类）
- 注释完整度（复杂逻辑、公共 API）
- 单一职责原则遵循度
- 开闭原则遵循度

## 分级标准

| 级别 | 含义 | 处理时机 |
|------|------|----------|
| 🔴 Critical | 必须立即修复（安全漏洞、数据丢失、崩溃） | 阻断合并 |
| 🟠 Major | 应在合并前修复（逻辑错误、性能严重问题） | 阻断合并 |
| 🟡 Minor | 建议修复（可维护性、风格） | 可后续修复 |
| 🔵 Info | 提示性建议（优化、最佳实践） | 仅记录 |

审查范围：函数/类/模块

🔴 Critical（N 项）

    影响：...

🟠 Major（N 项）
  [M-001] 行 XX: 问题描述

    修复建议：...

🟡 Minor（N 项）
  [m-001] 行 XX: 问题描述

## 与其他技能的协同
- 与 `metago-critique` 协同：审查过程应用 L1-L5 批判性分析
- 与 `metago-fact-check` 协同：检测虚构 API、不存在的函数（幻觉代码）
- 与 `metago-decision-lock` 协同：审查报告需通过决策锁校验
- 与 `metago-problem-trace` 协同：问题无限溯源至根本原因
- 与 `metago-security-audit` 协同：安全维度联动深度安全审计
- 与 `metago-refactor-suggest` 协同：可维护性问题联动重构建议

## 使用示例

**用户输入：** "请深度审查 src/auth.ts"

技能激活后按内置流程执行并输出结构化结果，可直接用于真实工作流。

## 安全与边界

本技能只输出审查报告与修复建议，不自动修改代码；重大缺陷需人工复核。

## 常见问题

**Q: 分级标准是什么？**

A: Critical 阻断合并 / Major 合并前修复 / Minor 建议修复 / Info 仅记录

**Q: 能替代人工 Code Review 吗？**

A: 不能，作为自动化辅助与人工复核结合

## 常见误区与不适用场景

- 误区：只贴一行代码就要求审查——缺少上下文只能给表层意见；
- 误区：把 Info 当必修项——Info 仅记录，不应阻塞合并；
- 误区：让本技能自动改代码——本技能只输出报告与建议；
- 不适用：运行时调试、压测与真实安全渗透（这些需专门工具）。

## 异常与边界处理

- 未提供代码或文件路径：要求用户提供代码片段或路径，不臆测代码内容；
- 文件超长：分段审查，并在报告中标注已覆盖的行范围；
- 语言或框架无法判断：先向用户确认技术栈再审查；
- 审查意见相互冲突：按严重级排序，冲突项标注“待人工裁决”；
- 不确定的结论一律标注置信度，禁止把推测写成事实。

## 运行保障（稳定性）

- 重试机制：执行结果不完整或格式异常时，按原输入自动重试 1 次，再失败则向用户说明并请补充输入；
- 超时处理：任务超出合理轮次时停止生成，输出已完成部分并标注未完成项；
- 错误恢复：输出中断时，基于已生成内容给出可继续的断点说明；
- 一致性保障：相同输入遵循固定流程与输出模板，关键结论标注置信度；
- 错误消息模板：输入缺失→"请提供要审查的代码片段或文件路径"；语言不明→"请说明使用的语言与框架"；超长输入→"内容过长，建议分段提交，本次审查范围：…"；
- 本技能不执行外部网络请求，最小权限运行，宿主平台的重试与超时兜底。

## 完整示例

**输入：** "深度审查 src/auth.ts"

**输出（节选）：**

```text
【深度代码审查报告】
V-001 [Major] SQL 注入
  位置：src/auth.ts:42
  问题：查询语句字符串拼接用户输入
  影响：可绕过认证、拖库
  修复：改用参数化查询（prepared statement）
V-002 [Minor] 未处理 Promise 异常
  位置：src/auth.ts:78
  修复：补 catch 并记录结构化日志
结论：Major 1 项（合并前必修）、Minor 1 项、Info 2 项
```

**Q: 审查超长文件怎么办？**

A: 分段审查并标注范围，最后汇总跨段的关联问题。

**Q: 多语言项目怎么审？**

A: 按目录/模块分组，先说明每组语言与框架，再逐组审查。

**Q: 大 PR 怎么拆分？**

A: 按提交或模块边界拆分，先审查核心改动，再查边界影响。

**Q: 不确定的问题怎么标？**

A: 标注“待确认”并给置信度，不写死结论，留人工裁决入口。

## 追问：为什么"可插拔架构"稍微复杂就要改内核？（只读诊断，已回答）
用户观察：R3 降级改了三版，级联路由也要改一堆设计；初衷是"底层接入用户任意策略/工具"，为何复杂功能总穿透内核？
- **根因 1（依赖倒置，最关键）**：项目自己记录在案 `扩展体系重构规格-20261120.md:15`「内核契约被可选插件（R3）的需求绑架；插件不是必需品，应先定内核再定插件」。旧体系里策略需求通过 hook 扩展点反向定义内核抽象（Decision 8-action / Signal / scope / sticky_target），所以每次降级语义调整都反向改内核。
- **根因 2（扩展点语义过载 + 声明执行脱节）**：6 个 invoke hook 承载 BAIL/WATERFALL/AROUND/PARALLEL 五种语义且只覆盖单 Effect 窗口（规格:14）；LifecycleEvent 声明 21 事件零消费（:13）。
- **根因 3（控制语义 vs 观察语义混淆）**：裁决/拦截（被消费）与通知（不消费）混在一套 hook 里 → 既要它拦截又要它观察，语义打架（`AGENT-总设计.md:62,307`）。
- **R3 三版时间线**：①全局单槽+Signal 信号链（11-17，a6bc4f8）→ ②同体系一天连修四坑 B1 串味/B2 标识/R3-6 写回/R3-7 带目标（11-18，2120f23 等）→ ③整体换宿主到 AOP 五角色 + Degradation 单一裁决者，review 又抓 typed 降级断点再修一次（11-20，3ccf77b）。印证用户"改三版"。
- **LLM 降级特别难的根因**：它是横跨 R3（发现故障/选级）+R4（网关切后端/REFUSE）+R2（Verdict/AOP 顺序/通知）的跨层状态机；熔断 allowed=False 会摧毁 P9 切 backup（必须写 fault + allowed=True 放行）；跨会话跨 Effect 目标状态、异步故障写入时机——任一环改动连锁破坏别处（`20261120-1322检查.questions.md:124`、`R3-可靠性.md:81,258`）。
- **解药（已拍板）**：三体系正交（Port=what / AOP=how / Lifecycle=when）+ 依赖单向（插件→装配→内核）+ 内核自足零策略 + 四要素齐全（`AGENT-总设计.md:61-66`、`规格:25`）。这是"新增能力内核零改动"的前提。
- **对级联路由的直接结论**：级联是"默认策略内部的多级编排"，正确做法是把它收进 R13 `IntentRecognition` 默认实现内部（策略层），对内核/总设只暴露**一个** IntentResult（单入口），不要把"级联阶段/逐级置信度"泄漏成内核 DTO 或新相位。这样符合"新增能力内核零改动"，避免重演 R3。若要保留逐级 trace，用 `Invocation.meta`/state `x-*` 扩展键记录（观察语义），不改内核结构。

## 追问 2（用户纠错核心）：为什么"稍微复杂就改其他模块内核"——抽象层级错配
- 用户两次强调的真问题不是级联本身，而是这个现象反复发生。定性回答：
- **本质**：可插拔插头开在"单个决策"层，而稍复杂的功能几乎都是"多个决策的编排"。编排塞不进决策插头 → 只能改插头本身（=内核契约）。R3 降级、级联路由都是编排，所以都撑破插头。
- **为何是"其他模块内核"**：模块按能力域纵向切分（R1~R13），但编排是横向的——降级横穿 R3+R4+R2，级联横穿 R12+R13+R8+总设。横向能力压在纵向模块上，必然同时碰到多个模块的契约面。
- **必然 vs 设计债**：必然部分＝跨模块编排总要有个地方定义共享契约（内核）。设计债部分（可修）：①R12 classifier 没调用 recognize()、注入路径与执行路径割裂（不自洽）；②四要素插头只覆盖"一个协议一个默认"，没有"多实现如何组合"的插头；③契约面过宽（逐级置信度想进 DTO/加相位，一改全校连锁）。
- **出路**：复杂度在组合层吸收、不下沉内核——级联做成 `cascade([rule, llm, fallback])` 组合器返回一个新 IntentStrategy，对内核仍是一个策略一个结果；框架已有组合算子（R12 seq/par/branch/budget）与 AOP 五角色，只是没用在意图识别上。

## 追问 5：用户对"组合"的最终定性（拍板）
用户回答上一轮二选一：「我想要的是想要哪个就用哪个，但是使用上通过组合的形式」。
- 定性：不是二选一——**挑选层（按需插拔）+ 使用层（组合串联）两层都要**；以组合算子为主，依赖声明退居辅助。上一轮二选一问法把用户窄化了，已纠正。
- **ToolLayer 契约定型（组合式）**：每个工具层自包含、可独立 `build() -> Program`（支撑"想要哪个用哪个"）；组合算子 `seq/par/branch/budget(layer...) -> 新 layer` 是唯一组装方式（支撑"通过组合使用"）；`provides/requires` 降级为可选声明，仅用于挑选时校验依赖齐不齐/冲突检测，不参与运行时强制装配。
- 关键洞察：组合算子是**通用层级抽象**——既能组合策略（熔断+重试）、也能组合能力层（R4+R6+R7）、也能组合架构（ReAct+Graph）。一套组合语义贯穿所有层级。用户示例：`seq(ModelCapability, RAGPipeline, ContextMemoryManager)` 或策略级 `seq(CircuitBreaker, RetryPolicy)`。R12 的"10 架构"实质是组合算子的预设配方。
- 对改造的影响：组合层(R12)定位从"编排器"收敛为"组合算子库"；核心层只需认 Program，不认 provides/requires。provides/requires 在装配期校验，不进运行时内核。

# 独立 code-quality-review 报告

> 审查对象：扩展体系重构（P1~P14，本次改动范围见任务书）
> 意图源：`docs/01-总览与设计/扩展体系重构规格-20261120.md`、`overviews/2026-11-20/扩展体系重构-口径卡.md`
> 审查方式：全量打开生产代码 + 关键测试，并对 P9 最高风险项做实际运行复现；未修改任何代码。

## 结论

**Blocker=2 / Should=4 / Nit=3；是否通过：否（Blocker≠0）。**

两个 Blocker 都是"声明兑现/功能断点"级别：一个是 P9 降级四坑中 **R3-7 的 typed 降级路径在真实 retry/timeout 出口断裂**（Degradation 根本不被触发）；另一个是 **16 个 Lifecycle 通知点中仅 3 个真正送达总线，其余要么无 emit、要么 emit 到无人接的回调**——即本次重构要根治的"声明与执行脱节"在新体系原样重现。二者均被现有"全绿"测试掩盖（E2E 用 Warden 模拟故障、通知只测 model 相位）。

## 七维扫描发现

### Blocker

- **[src/aop/container.py:168, 174-187] + [src/harness/resilience/retry.py:76-81] + [src/harness/resilience/timeout.py:48-53] — R3-7 typed 降级路径断点：Envelope 层写入的故障无人消费，Degradation 永不被调用。**
  - 现象：`RetryPolicy.wrap`/`Timeout.wrap` 作为 Envelope，是在 `await next(inv)` **返回之后**才把 `FaultRecord(reason, failed_target)` 写进 `inv.meta`。但容器只有两处消费 fault：`_guard_phase` 在 `next()` **之前**检查（`container.py:180`），`_center` 在 core 返回时检查（`container.py:168`）——而 `_center` 是 Envelope 的**内层**，那时 retry/timeout 还没写 fault。两处都错过后，`_guard_phase:187` 直接 `return await next(inv)`，故障记录就此烂在 meta 里。
  - 后果：真实 retry 耗尽 / timeout 故障不会因为 `failed_target` 剔除目标、不会写 `routing_target`、不会重路由到 backup、永远到不了 REFUSE。**P9 R3-7 的语义（故障带出→settle 剔除→选级）整条断裂**，规格 P9「retry 耗尽/timeout 降级信号必须携带 failed_target，settle 据此剔除」未兑现。
  - 实证复现（core 恒返回 retryable 失败 + `RetryPolicy(max_attempts=2)` + `Degradation`）：`result.ok=False, code=RETRYABLE_ERR`，`fault=FaultRecord(reason='retry_exhausted', failed_target='primary')`，但 **`routing_target=None`**，Degradation 的 `recover/select` 完全未触发。
  - 为何测试全绿却漏掉：`tests/r3/test_e2e_degrade.py:36-45` 用 `_FaultWarden` 在 **Warden 阶段**写 fault，恰好命中 `_guard_phase` 检查点，绕开了断点；单测 `test_degrade/test_degrade_pipeline` 只直接调 `Degradation.select()`，不经过容器。
  - 改法：按规格 §3/口径卡 §5 的固定顺序把 **Salvage 提升为最外层兜底**（`Envelope(后) → Salvage`），使其能捕获整条链（含 Envelope）写出的故障并裁决重路由；或至少在 `_guard_phase` 的 `next()` 返回后补一次 `fault & !routing_target → _apply_salvage + 重路由`。必须新增**真实 RetryPolicy/Timeout 故障源**的端到端用例（primary 零调用、backup 被调用、REFUSE 真拒答），不能用 Warden 模拟替代。

- **[src/hooks/lifecycle.py:29-54] + [src/runtime/runner.py:181, 296, 312, 347, 386, 389, 435, 467, 521, 565, 592] + [src/harness/tools/] — 16 通知点大面积不投递：仅 3 个相位真发到总线，契约漂移，功能遗漏。**
  - 全 src 实际 emit 到 LifecycleBus 的只有 3 个：`invoke_rejected`（`container.py:124`）、`before_model`/`after_model`（`gateway.py:215,232`，且需装配层显式传 `bus`，默认 None 不发）。
  - Runner 通过 `notify` 回调发出 9 个相位（child_spawn / child_done / cancelled / budget_check / wait_human / state_fold / session_start / resumed / session_end），但**全仓库没有任何代码把 `notify=` 接到 LifecycleBus**（`grep -rn 'notify=' src` 为空；`runner.py:181` 缺省是 no-op lambda）。demo_r2、test_e2e_wiring 等所有装配写法都未接 → 这 9 个相位从未送达任何订阅者。
  - 另 4 个相位 `user_prompt`、`before_tool`、`after_tool`、`tool_error` 在所有生产代码中**零 emit**（仅存在于枚举声明与注释）。`tests/r2/test_lifecycle.py` 只断言枚举数量=16 和总线机制本身，`test_e2e_wiring.py:155` 只覆盖 model 相位。
  - 后果：规格 P2「Runner 发会话/轮次/控制流系列、R5 发 tool 系列」「纯通知、异常隔离、返回值不消费」的 when 体系，13/16 相位形同虚设。这正是规格 §1.1 要根治的"声明 21 个事件、全 src 零消费、零 dispatch"根因在新体系的重现。
  - 改法：提供装配入口把 `Runner.notify` 桥接到 `LifecycleBus.emit`（把 raw 相位名归一为 `Notice`），在 R5 工具执行路径补 tool 三相位与 `user_prompt` 触发点；补"Runner 相位真到达订阅者"的端到端用例。

### Should

- **[src/aop/container.py:158-169, 182] — invoke_rejected 未在异常与终止失败出口发，审计盲区残留。** 规格 P3 / 口径卡 §5 要求"invoke_rejected 在拒绝/异常时必发"。当前仅 Warden `Verdict(allowed=False)`（`container.py:182`）会发；core 抛异常且无 Salvage 时（`:163` 直接 `raise`）、以及 `BULKHEAD_FULL`/`IDEMPOTENCY_REQUIRED`/`INVALID_EFFECT` 等终止失败 Result 均未发通知。改法：在容器统一的失败/异常出口发 invoke_rejected（payload 带 reason 与失败码），与 Warden 拒绝共用一条通知路径。

- **[src/aop/container.py:148-172] — Salvage 执行位置与规格固定顺序不符（也是 Blocker#1 的根因）。** 规格 §3 / 口径卡 §5 固定顺序 `… Port call → Envelope(后) → Salvage(异常时)`，Salvage 应是最外层异常/失败出口；实现把 `_apply_salvage` 放在 `_center` 内层，异常时先于 Envelope 后处理执行（如 CircuitBreaker.observe 记到的是兜底后的成功结果），且导致 Envelope 写出的 fault 无法被兜底捕获。改法随 Blocker#1 一并调整。

- **[tests/r3/test_e2e_degrade.py:75-86] — 缺 REFUSE 真拒答端到端回归，断言覆盖不齐。** 文件仅 2 个用 `_FaultWarden` 模拟、切到 backup 的用例；规格 P9 明确要求保留 R3-E01/E02/E03 且「REFUSE 真拒答不许放水」。目前没有"primary、backup 全故障 → REFUSE → 网关零后端调用 / 真拒答"的 E2E（REFUSE 只在 `select()` 单测层验证）。改法：补端到端用例，断言 primary.calls==0、backup.calls==0、输出为拒答结果。

- **[src/harness/model/capability.py:52-64] + [src/aop/container.py:63] — "Registry 同源（两表统一）"靠调用方手工 install，最常见装配写法下不成立。** `ModelCapability.install(container, reg)` 能把同一份 registry 写给容器（`capability.py:62-63`），但 E2E / demo 普遍直接 `cap.gateway()` + `AOPContainer(gw.as_call())`，未调 `install()` → `container.registry` 仍为 None，而 gateway 持有独立 `ModelRegistry`。规格 P6「共用同一 Registry 实例」在默认路径未兑现。改法：装配入口强制同源，或在 `as_call()`/构造时由 gateway 注入其 registry。

### Nit（≤3）

- **[tests/r4/test_model_registry.py:139] — 测试 docstring 仍写"as_call 从 ctx.degrade_target 读降级目标"**，而实现已改为 `inv.routing_target()`（`gateway.py:210`），注释与契约漂移，建议更新。
- **[src/harness/model/gateway.py:141] — `degrade_target` 参数注释仍写"来自 dispatch 回传"**，但 `dispatch` 已在 P1 删除，现来源是 typed `routing_target`；注释残留旧语义。
- **[src/aop/container.py:107-116, 189-203] — 洋葱层工厂的 `type: ignore` / 动态 `cast` 较集中**（`register()` 的字符串分派、`_session_view` 鸭子投影），可读性/可维护性小瑕疵，非功能问题。

## 接线四问核对

1. **三层接线（内核 ↔ 装配 ↔ 插件）**：内核侧 Effect union / Runner 分派已就位；插件侧九插件已迁 AOP 五角色、`v5.py` 已删、零 v1/v5 字眼；但**装配层缺关键一环**——Runner.notify 没有任何生产接线（见 Blocker#2），AOPContainer.registry 同源靠手工 install（见 Should#4）。→ **有断点**。
2. **Lifecycle 通知相位消费**：AOP→invoke_rejected、R4→model 两相位能真发；Runner 9 相位发到 no-op、4 相位零 emit（见 Blocker#2）。→ **大部分断点**。
3. **降级 typed 路径（FaultRecord → Degradation.select → RoutingTarget → 网关）**：Warden 阶段故障链路完整可跑（E2E 已验）；但 Envelope 阶段（retry/timeout）故障写 meta 后无消费者，typed 路径在"故障上报→Salvage"这一跳断裂（见 Blocker#1）。网关侧消费 `routing_target`（REFUSE 零调用/未注册 TargetUnresolved 不回退）实现正确。→ **部分断点（最高风险）**。
4. **checkpoint / 快照迁移**：离线迁移工具 `tools/migrate_snapshot.py` + `tests/r1/test_snapshot_migration.py` 已交付，覆盖 kind→port/disposition、幂等、restore 端到端；Effect tagged union + Disposition + fold 三分支 / runner match 就位。→ **兑现**。

## 结论

**Blocker=0 / Should=2 / Nit=2；是否通过：通过（Blocker=0）。**

上一轮两个 Blocker 均为真实修复，不是"测试放水式"清零：

- **Blocker#1（R3-7 typed 降级断裂）**：Envelope 在 `await next()` 之后写入的 fault，现由**链外 Salvage 兜底**消费，真实 RetryPolicy / Timeout 耗尽均能写 `routing_target` 并重路由到 backup，primary+backup 全故障逐级剔除收敛到 REFUSE，零静默回退。

但修复引入 **1 个 Should 级副作用**（链外重路由重跑整条链，导致状态型 Warden 二次执行、幂等键自命中，特定插件组合下降级失效），并遗留 **1 个装配层 Should**（生产/示例未接线）与 **2 个 Nit**。全量 `pytest` 553 通过。

## 原 Blocker 复核

### Blocker#1：R3-7 typed 降级断裂 —— **通过**

**代码核对：**

1. 链外兜底已落地。`container.py:227-256 _build_chain()` 仅构建 `Prelude(外)→Warden→Envelope→Refiner→Port(内)`；Salvage **不在链内**，而在 `container.py:258-299 _call()` 中于整条链返回后统一消费（`_call` docstring :261-264 明确"只有整条链返回后才知道最终失败目标"）。这正是原 Blocker"fault 烂在 meta 无人消费"的根因修复。
2. fault 消费点齐备：`_call:272` 读 `inv.fault()`；`:273-279` 当已有 `routing_target` 且非 refuse 时，**用 `current.target` 覆盖写回 failed_target**（逐级剔除关键，不依赖 Envelope 静态 `failed_target_of`）；`:283-292` pop 旧 target → `_apply_salvage` 选级 → pop fault → 重跑 chain。
3. Degradation 唯一裁决者 + 四坑：`defenses.py:117-149`（B1 按 session_id 独立 available、R3-6 `discard` 后写回 `state["available"]`、B2 注册名由上游派生、`:148-149` pick 全无则 REFUSE）；`:151-169 recover()` 写 typed `routing_target`，REFUSE 返回 `Result.failure("REFUSED")`，绝不编造答案。
4. 上游 fault 携带 failed_target：`retry.py:76-81`（耗尽写 `retry_exhausted` + `_failed_target_of`）、`timeout.py:48-53`（超时写 `timeout` + `_failed_target_of`），二者均在 `await next()` 返回/异常之后写入 —— 恰是原 Blocker 的断点位置，现由链外兜底覆盖。
5. 网关 typed 消费不变：`gateway.py:209-213` 只读 `inv.routing_target()`；`:164-173` REFUSE → RefuseExecution、未注册 → TargetUnresolved，零静默回退。

## 修复引入的新问题

### Should-新1：链外重路由重跑整条链 → 状态型 Warden 二次执行，特定插件组合下降级失效

`_call:292 result = await chain(inv)` 重路由时**重跑整条链，含 Warden/Prelude**。状态型 Warden 在同一 Invocation 内被二次执行：

- **实测复现 D**（`Idempotency(store={})` + `RetryPolicy(max_attempts=1)` + `Degradation`，effect 带 `idempotency_key="K"`）：
  - 首轮 `Idempotency.guard(K)` → 首次登记、放行 → primary 失败 → retry 耗尽写 fault → 链外选级写 `routing_target=backup`、重跑。
  - 重跑时 `Idempotency.guard(K)` → **命中自身首轮登记的 K** → `Verdict(allowed=False, "duplicate_side_effect")`，`_guard_phase` 短路返回 `INVOKE_REJECTED`。
  - 链外据此写 `failed_target=backup` → 剔除 backup → `routing_target=REFUSE`，最终 `backup.calls=0`、输出失败。
  - 位置：`defenses.py:294-300 Idempotency.guard`（`check_and_mark` 重复登记）、`container.py:292`（重跑整链）。
- `Watchdog`（`defenses.py:346-351` 每次 guard 都 `observe` 并累积 history）同理，重跑会重复计数、可能误触发 `watchdog:repeat`，属同类风险。
- **影响面**：仅在"状态型 Warden + 降级重路由"共存时破坏降级正确性；P9 四坑单测与常见 LLM 降级（无幂等键）不受影响，故判 Should 而非 Blocker。若把"P4 九插件任意组合共存"视为硬门禁，可升格为 Blocker，请主控定夺。
- **建议**：重路由时只重跑 `Envelope→core` 段而跳过 Warden/Prelude；或 Warden 预裁决后以具名标记（如 `meta["_wardens_done"]`）让本 Invocation 后续 guard 短路放行。

## 剩余发现

### Should

- **Should-新1**：见上（幂等/Watchdog 型 Warden 与链外重路由冲突）。
- **Should-残2（生产装配未接线）**：`runner_notifier` 在 `src/` 与 `tests/demos/` 中**零调用**（仅 `tests/r2/test_lifecycle_wiring.py:54,68` 使用）；`demo_r2.py:54` 构造了 bus 却只订阅 `invoke_rejected`，未接 `runner_notifier`；`ModelGateway` 的 `bus` 默认 `None`（`gateway.py:84,109`），`AOPContainer` 的 `bus` 亦默认 None。真实运行时除 `invoke_rejected` 外的 15 个相位需装配层显式接线才会投递。`ModelCapability.container()`（`capability.py:89-95`）已提供同源 registry + bus 的标准容器工厂，但 demo/装配示例未演示"bus → ModelCapability(bus=) → Runner(notify=runner_notifier(bus))"完整链路。规格定位 R12 设计态、本次零代码，故不判 Blocker；建议补统一装配入口或在 demo 演示完整接线，否则"声明与执行脱节"根因在示例层仍可见。

### Nit

- **Nit-残1（声明未兑现的注释漂移）**：修复摘要声称"Nit#1 已修"，但 `tests/r4/test_model_registry.py:3` docstring 仍写"gateway.as_call() 从 `ctx.degrade_target`（具名桥接字段，Host 从 scope.target 写入）读降级目标"，与实现 `inv.routing_target()`（`gateway.py:210`）及 P1 已删除的 Host/scope.target 直接矛盾。声明与执行不一，建议更正。
- **Nit-新2（trace reason 语义略偏）**：REFUSE 场景下 `invoke_rejected` 的 `reason` 记录的是首次故障 reason（如 `retry_exhausted`），而非最终裁决 `refuse`。实测 A2：`rejected=['retry_exhausted']` 但结果为 REFUSED。源于 `container.py:277` 沿用 `existing_fault.reason`。仅进 trace，不影响功能。

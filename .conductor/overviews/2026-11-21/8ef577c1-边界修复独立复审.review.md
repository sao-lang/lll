## 1. Blocker（必须修复，阻断合入）

### B-1 【Blocker / 新引入回归】单 store 合并导致 checkpoint 快照被写坏，恢复路径崩溃

**证据**
- `src/api/runtime.py:91-99`：`shared_store = mgr.store`；`store = CheckpointEventStore(mgr, inner=shared_store)` —— manager 与 inner 指向**同一个** EventStore。
- `src/api/wiring.py:256-257`：`self.inner = inner`；`self._mgr = manager`（同一 store 实例）。
- `src/api/wiring.py:264` 与 `wiring.py:267`：`save()` 对**同一个 key** 连续写两次：
  1. `await self.inner.save(session_id, snapshot)` —— 写 R1 原生快照，`state.messages` 是 **dict**（由 `checkpoint()` 的 `_plain()` 规范化）；
  2. `await self._mgr.save(replace_dto_fingerprint(dto, ...))` —— 经 `CheckpointManager.save → _to_json_snapshot`，其 `src/harness/durability/checkpoint.py:59` 为 `"messages": list(state.messages)`，`state.messages` 此时是 `Message` **对象**（未经 `_plain`），把第一次的好写入覆盖。
- 改动前（HEAD~1）`_inner` 与 `_mgr` 是**两个不同 store**，`load()` 从 `_inner` 读到的是好快照；本次 S7"单 store"改动把两次写合到同一 key， corruption 暴露。

**实测（自编探针，PYTHONPATH=src）**
```
save 前 snapshot.state.messages[0] 类型: dict
落盘 state.messages[0] 类型: Message        ← 被第二次写覆盖
restore_checkpoint 失败: TypeError 'Message' object is not subscriptable
```
即任何经 `store.load()` 的恢复（`src/runtime/runner.py:715-718`）都会崩。

**为什么是问题**：R10 checkpoint 恢复是本契约 FR-2/S7 声称要修好的能力，本次改动**新引入**了一个静默数据损坏回归。测试 `tests/r11/test_wiring.py:128` 用 `CheckpointEventStore(mgr)`（不传 inner，inner 自建独立 store），刻意/无意地保留了"双 store"从而**掩盖**了生产装配的单 store 路径——同一 test 名 `test_checkpoint_store_save_and_replay` 只断言 fingerprint 相等（`test_wiring.py:136`），从不调用 `restore_checkpoint()`，所以验不出损坏。接线四问之"失败路径是否 fail-closed"：这里连 fail-closed 都不是，是静默坏数据。

**修复建议**：`save()` 只写一次。要么删掉 `inner.save` 只保留 mgr 路径并修 `_to_json_snapshot`（`messages` 用 `_plain` 规范化），要么删掉 `mgr.save` 只保留 `inner.save` 并让 `load`/`manager()` 从同一来源读。补一条 **走共享 store + `restore_checkpoint()`** 的失败测试（断言恢复出的 `state.messages[0].role == 'user'`），并让 `test_checkpoint_store_save_and_replay` 用 `CheckpointEventStore(mgr, inner=mgr.store)` 复现生产接线。

### B-2 【Blocker / AC-5 部分未兑现】生产路径 seq 100% 仍是本地合成计数，"优先取 R1 序号"是空转逻辑

### B-3 【Blocker / 接线四问不过关】"生产 CRITICAL 真执行"是测试直调 Registry 绕过 Runner，装配链"最后一公里"未接

**证据**
- `src/api/runtime.py:102-104`：`assemble_runtime` 构造 `wired_tools = ToolRegistry(sandbox=sec.sandbox, human=approving, audit=auditing)`，挂在 `AgentRuntime.tools`。
- 但 `src/api/runtime.py:106`：Runner 的 `call` 来自**入参**（`call: CallFn`），全库无任何代码把 `rt.tools` 接成 dispatch/call（grep `assemble_runtime|capability_tools|make_dispatch` 全仓库，只有 builder 与测试调用，`capability_tools()` 返回的能力也从未被任何 `make_dispatch` 消费）。
- 所谓"生产路径"测试 `tests/r11/test_boundary_fix.py:191-202`：`rt.tools.register(...)` 后直接 `asyncio.run(rt.tools.call(...))` —— **完全绕过 Runner**。`test_wiring.py:234-261` 同样直调 `tools.call()`，并在 257 行**手工重建** `ToolRegistry(sandbox=LocalSandbox(), ...)`。
- 接线四问：
  - 生产调用者是谁？——**没有**。除 `AgentBuilder.runtime()` 转调 `assemble_runtime`（`builder.py:154-163`）外，无真实调用者；builder 也不把 tools 接进 call。
  - 真实实现在哪？——ToolRegistry 实现正确，但**不在 Runner 执行链上**。
  - 是否造假绿？——是。测试直调 registry 证明"registry 能跑 CRITICAL"，但证明不了"生产 agent 跑一次 CRITICAL 工具会走审批+沙盒+审计"。

**实测（自编探针，跑真实 `rt.runner.run()` 发 CRITICAL tool Invoke）**
```
runner 实际调用的 call: ['INJECTOR_CALL']     ← 走注入的 call，不是 registry
registry.audit 事件数: 0                       ← 审批/沙盒/审计全部被绕过
```
即真实 Agent 运行中，`Invoke(port=tool, danger=CRITICAL)` 不会经过那条被声称"修好"的审计/沙盒/审批链。

**为什么是问题**：AC-6 声称"profile('regulated') 后生产路径 CRITICAL 审批通过真执行"，B2 声称"两条装配链合一"。实际只合了"sandbox 不再为 None"这半条；profile 装的端口进 `Agent._registry`（`builder.py:72`），`assemble_runtime` 另造一个 ToolRegistry，而 Runner 的 `call` 又与二者都无关——**三条链**。审计全覆盖（R9-G3 100%）、CRITICAL 强制沙盒等安全保证在实际执行中不成立。

**修复建议**：在 `assemble_runtime` 内提供缺省 `call`：当调用方未注入时，用已接线的 `wired_tools` 构造 dispatch（如 `make_dispatch({"tool": wired_tools.as_call()})` 或等价适配）注入 Runner；把 `test_production_critical_executes_via_security_capability` 改为跑一个真实 `Session`（`Invoke(port=tool, danger=CRITICAL)` → `rt.runner.run()`），并断言 `rt.audit.events()` 非空、`sandbox.calls`/审批被触发。这才会让 AC-6 名副其实。

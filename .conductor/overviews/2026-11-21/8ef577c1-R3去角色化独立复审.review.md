## 三、Should（建议修复，不单独阻断）

### S1【行为等价】core 抛异常 + 配置 degradation 时，新版直接穿透异常，旧版会降级到 backup

- **证据**：
  - 新版 `src/harness/resilience/executor.py:202-212`：`_budgeted_call` 的 `except Exception` 只做 `breaker.observe_outcome(failure)` 后 `raise`（注释称"交降级链处理，不吞异常"）；`executor.py:242` `_invoke` 直接 `await self._budgeted_call(inv)`，**无 try/except 接住降级**。
  - 差分探针（同一 ladder/available=primary,backup、core 抛 RuntimeError）：
    - 新版（工作区）：`RAISED RuntimeError 'boom'  target=None`
    - 旧版（HEAD/AOPContainer）：`OLD RESULT ok=True  target=backup`（旧 `_center` try/except → `_apply_salvage` → `Degradation.recover`）
  - 根因：旧 `CompositeCall._center` 有 `except Exception → _apply_salvage` 把异常交降级；新版执行器编排链缺少这一环，注释与实现不符。
- **影响面评估（为何只列 Should）**：
  - 四坑 fault 均来自 `Result.failure`（retry/timeout/rate/breaker），**不经异常路径**，故四坑断言与降级重路由不受影响（已实测 670 passed + 四坑用例全绿）。
  - `breaker-only + 异常` 新旧等价（均 raise + failures=1，见 `tests/r3/test_capability.py:190-198`），该行为被测试锁定。
  - 生产 core = `gateway.as_call()`，其 `_center` 自带 `try/except BaseException → raise`（`gateway.py:243-245`），异常本属边界场景。
- **建议**：在 `_invoke` 包住的 `await self._budgeted_call(inv)` 外补 `except Exception`：写 `FaultRecord(reason="invoke_exception", failed_target=...)` 后走 `_apply_recovery` 重路由；或同步修正 `_budgeted_call:209` 注释，明确"异常不进降级链"为有意决定，并补一条行为测试固化。
